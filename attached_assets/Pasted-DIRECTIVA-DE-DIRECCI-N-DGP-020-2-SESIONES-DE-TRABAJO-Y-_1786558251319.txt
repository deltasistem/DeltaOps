==================================================
1. OBJETIVO
==================================================

Implementar un mecanismo confiable, auditable y offline-first para registrar las SESIONES REALES DE TRABAJO de una Orden de Trabajo.

El objetivo es poder determinar posteriormente:

- cuándo comenzó una sesión;
- cuándo se pausó;
- cuándo se reanudó;
- cuándo terminó;
- cuánto tiempo estuvo activa;
- cuánto tiempo estuvo pausada;
- cuánto tiempo transcurrió;
- qué identidad realizó la sesión;
- sobre qué OT;
- sobre qué activo;
- en qué tenant;
- cuándo ocurrió en el dispositivo;
- cuándo fue registrada por el servidor.

La información debe permitir posteriormente calcular:

TIEMPO EFECTIVO

TIEMPO PAUSADO

TIEMPO TRANSCURRIDO

sin depender de inferencias posteriores.

==================================================
2. PRINCIPIO DE FUENTE DE VERDAD
==================================================

La fuente de verdad futura para los intervalos de trabajo serán:

TRAMOS DE SESIÓN APPEND-ONLY

Los eventos de Workflow y la bitácora de la OT:

NO serán la fuente de verdad para calcular intervalos.

Pueden utilizarse como:

- señal auxiliar;
- evidencia de consistencia;
- diagnóstico;
- Timeline.

No reconstruir sesiones únicamente desde:

`ocurridoAt` de bitácora.

Esto fue identificado como GAP-CLOCK en DGP-020.

==================================================
4. ESTADOS
==================================================

La sesión debe tener un ciclo inequívoco.

Evaluar y utilizar el diseño aprobado:

ABIERTA
PAUSADA
CERRADA

Una sesión:

ABIERTA
→ PAUSADA
→ ABIERTA
→ PAUSADA
→ ABIERTA
→ CERRADA

Debe permitir múltiples ciclos de pausa/reanudación.

No permitir:

ABIERTA → ABIERTA
PAUSADA → PAUSADA
CERRADA → cualquier estado operativo

salvo que exista una operación explícita y autorizada definida por contrato.

No inventar reapertura.

5. COMANDOS
==================================================

Implementar únicamente los comandos necesarios:

- abrir sesión;
- pausar sesión;
- reanudar sesión;
- cerrar sesión.

Utilizar los nombres y namespaces canónicos existentes.

`modulo.tiempos.sesion.cerrar`

No crear comandos redundantes.

==================================================
6. VALIDACIÓN DE IDENTIDAD
==================================================

Una sesión de trabajo debe estar vinculada a una identidad canónica.

Al abrir una sesión:

1. obtener identidad desde la sesión autenticada;
2. no aceptar identityId arbitrario desde frontend como autoridad;
3. verificar que la identidad está activa;
4. verificar membresía activa;
5. verificar tenant;
6. verificar que la identidad está asignada a la OT según el contrato vigente;
7. verificar que el usuario tiene capacidad para operar la OT.

No permitir que un técnico abra una sesión sobre una OT asignada a otro técnico.

Si el contrato actual contempla una excepción legítima para supervisor/administrador:

respetarla según las capacidades existentes.

No inventar nuevos permisos.

==================================================
7. RELACIÓN CON OT
==================================================

Una sesión debe pertenecer a una OT válida.

Validar:

- OT existente;
- tenant correcto;
- estado de OT compatible con iniciar trabajo;
- activoId de la OT;
- identityId asignado.

No modificar silenciosamente el estado de la OT para crear una sesión.

Si para abrir una sesión es necesario cambiar el estado de la OT:

detenerse y documentar el contrato requerido.

No inventar una transición.

==================================================
8. RELACIÓN CON ACTIVO
==================================================

La sesión debe conservar:

OT
+
activoId

El activo debe provenir del contexto de la OT.

No aceptar un activo arbitrario enviado desde frontend.

Esto permitirá posteriormente:

Activo
→ OT
→ sesión
→ tiempo efectivo

y posteriormente:

Activo
→ costo de mantenimiento.

No crear una segunda relación OT-Activo.

==================================================
9. TIMESTAMPS — CRÍTICO
==================================================

Cada evento de sesión debe distinguir:

A. `ocurridoAt`

Hora real en que el evento ocurrió en el dispositivo/campo.

B. `registradoAt`

Hora en que el servidor recibió/registró el hecho.

No utilizar únicamente la hora de sincronización.

Para operaciones online:

ocurridoAt puede ser generado por cliente con validación.

Para operaciones offline:

ocurridoAt debe conservar la hora del dispositivo.

registradoAt será la hora del servidor cuando sincronice.

Nunca reemplazar ocurridoAt por registradoAt.

10. RELOJ DEL DISPOSITIVO
==================================================

Implementar las reglas definidas en Discovery para reloj sospechoso.

Evaluar y aplicar la política aprobada:

- detectar timestamps futuros;
- detectar retrocesos;
- detectar inconsistencias;
- marcar anomalías sin destruir el hecho.

NO modificar silenciosamente timestamps.

Si un timestamp es sospechoso:

el hecho puede conservarse con marca de anomalía según el diseño aprobado.

No convertirlo automáticamente en una hora de servidor.

==================================================
11. MONOTONICIDAD
==================================================

Dentro de una sesión:

Los timestamps de eventos deben respetar el orden temporal lógico.

Ejemplo válido:

09:00 ABRIR
10:00 PAUSAR
10:15 REANUDAR
11:00 CERRAR

Ejemplo inválido:

09:00 ABRIR
10:00 PAUSAR
09:45 REANUDAR

Debe existir una regla determinista.

No borrar el evento inválido.

Debe quedar registrado como inconsistencia/rechazo según el contrato.

==================================================
12. TRAMOS
==================================================

La duración debe calcularse desde tramos.

Ejemplo:

ABRIR
09:00

PAUSAR
10:00

REANUDAR
10:15

CERRAR
11:00

Resultado:

Tiempo transcurrido = 2h
Tiempo pausado = 15m
Tiempo efectivo = 1h45m

No calcular:

11:00 - 09:00 = 2h

como tiempo efectivo.

==================================================
13. MÚLTIPLES PAUSAS
==================================================

Debe soportarse:

ABRIR
PAUSAR
REANUDAR
PAUSAR
REANUDAR
CERRAR

El cálculo debe sumar todos los tramos.

Ejemplo:

Trabajo:
09:00–10:00 = 1h
Pausa:
10:00–10:10 = 10m
Trabajo:
10:10–11:30 = 1h20m
Pausa:
11:30–11:45 = 15m
Trabajo:
11:45–12:00 = 15m

Tiempo efectivo = 2h35m
Tiempo pausado = 25m
Tiempo transcurrido = 3h

Los resultados deben derivarse de los hechos almacenados.

14. IDEMPOTENCIA
==================================================

CRÍTICO.

Cada operación debe tener:

opId

y debe utilizar el patrón durable de idempotencia existente.

Dos solicitudes simultáneas con el mismo opId deben producir:

EXACTAMENTE UN HECHO.

Probar carrera real contra PostgreSQL.

No confiar únicamente en:

- frontend;
- debounce;
- bloqueo visual;
- memoria.

La protección debe existir en backend/BD.

==================================================
15. CONCURRENCIA
==================================================

Probar escenarios como:

Dos `abrir` simultáneos.

Dos `pausar` simultáneos.

`pausar` + `cerrar` simultáneos.

Dos `cerrar` simultáneos.

Dos operaciones diferentes con opId diferente sobre la misma sesión.

El resultado debe ser determinista.

No permitir dos estados finales incompatibles.

NO permitir sesiones abiertas concurrentes para la misma combinación:

tenant + OT + identity.

Si el contrato requiere otra política:

documentarla y justificarla.

No permitir solapes silenciosos.
