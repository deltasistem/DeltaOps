OBJETIVO:

Conectar los movimientos físicos de materiales/repuestos de Inventario con los hechos económicos de module-costos.

El resultado debe permitir demostrar:

ARTÍCULO
→ CANTIDAD CONSUMIDA
→ MOVIMIENTO DE INVENTARIO
→ OT
→ ACTIVO
→ COSTO UNITARIO SNAPSHOT
→ COSTO TOTAL
→ HECHO ECONÓMICO

No modificar la fuente de verdad de Inventario.

No duplicar el dominio de Inventario.

No convertir module-costos en un inventario paralelo.

7. SNAPSHOT
==================================================

Al materializar el consumo:

congelar:

- artículo;
- cantidad;
- unidad;
- costo unitario;
- costo total;
- moneda;
- fuente;
- referencia del movimiento;
- OT;
- activo;
- fecha;
- identidad;
- evidencia.

Posteriores cambios del costo promedio ponderado NO deben modificar el hecho histórico.

Ejemplo:

Salida:
10 unidades

Costo promedio:
"35000.123456"

Costo materializado:

"350001.234560"

Posteriormente el costo promedio cambia.

El hecho histórico debe continuar mostrando:

"350001.234560"

No recalcular automáticamente.

==================================================
11. MONEDAS
==================================================

El costo proviene de DGP-021.0 por:

artículo + moneda.

Si existen varias monedas para un mismo artículo:

NO elegir arbitrariamente.

NO convertir.

Determinar comportamiento correcto:

- exigir moneda;
- devolver varias alternativas;
- o marcar GAP.

La decisión debe estar sustentada por el contrato real.

Nunca sumar monedas distintas.

==================================================
13. DEVOLUCIONES
==================================================

Investigar específicamente cómo Inventario representa devoluciones.

componerlo.

Nunca borrar el hecho económico original.

==================================================
14. ANULACIONES
==================================================

Si el movimiento origen se anula después de materializar el costo:

no borrar el hecho económico.

Debe existir un mecanismo de compensación/anulación compatible con module-costos.

El resultado debe permitir reconstruir:

hecho original
+
anulación/corrección

Si el contrato de Inventario no permite detectar esta situación:

documentar GAP.

==================================================
15. IDEMPOTENCIA
==================================================

La materialización debe ser idempotente.

Utilizar el identificador de operación/origen apropiado.

Definir una identidad determinista para:

Movimiento Inventario
→ Hecho Económico

No generar múltiples hechos para el mismo consumo.

Probar:

mismo evento dos veces.

Resultado:

exactamente un hecho.

==================================================
16. CONCURRENCIA
==================================================

Probar contra PostgreSQL real:

- dos materializaciones simultáneas del mismo movimiento;
- dos movimientos diferentes;
- mismo movimiento con diferentes opId;
- materialización + anulación simultánea cuando aplique.

Resultado determinista.

No confiar solamente en validaciones frontend.
