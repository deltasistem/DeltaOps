DIRECTIVA OFICIAL — DELTAOPS LITE-04
«IMPLEMENTACIÓN DEL PREOPERACIONAL Y CHECKLIST OPERACIONAL»

ESTADO DEL PROGRAMA

DeltaOps Lite-03 está cerrado con PASS.

LITE-03 transformó la experiencia visual y operacional de la plataforma:

- navegación por proceso;
- Home accionable;
- contexto de centro de costos;
- Activos simplificados;
- ficha operacional del equipo;
- Design System;
- tema claro/oscuro;
- responsive mobile-first;
- seis roles existentes conservados.

AHORA comienza DELTAOPS LITE-04.

OBJETIVO PRINCIPAL

Implementar el flujo operacional:

EQUIPO
→ PREOPERACIONAL
→ CHECKLIST
→ RESULTADO
→ HALLAZGO

El objetivo es que DeltaOps pueda representar digitalmente el proceso que actualmente se realiza mediante formatos, Excel, Forms y otros mecanismos operativos.

IMPORTANTE:

Esta fase NO debe convertirse en una reconstrucción completa de mantenimiento.

No implementar todavía:

- ciclo completo de OT;
- asignación avanzada;
- ejecución de OT;
- aprobación/cierre de OT;
- indicadores nuevos;
- costos nuevos;
- combustible;
- inventario nuevo;
- nuevos roles;
- hardening de infraestructura;
- cambios de RLS;
- cambios de RBAC estructural.

Esos procesos serán fases posteriores.

==================================================
2. PRINCIPIO ARQUITECTÓNICO
==================================================

El preoperacional NO será un módulo paralelo.

Debe componerse sobre las capacidades existentes.

La arquitectura objetivo es:

ACTIVO
↓
PLANTILLA DE PREOPERACIONAL
↓
CHECKLIST
↓
RESPUESTAS
↓
EVIDENCIA / OBSERVACIÓN
↓
RESULTADO
↓
HALLAZGO SI CORRESPONDE

El activo sigue siendo la fuente de identidad del equipo.

La plantilla define QUÉ se debe revisar.

La ejecución define QUÉ ocurrió.

El hallazgo define QUÉ problema fue encontrado.

No duplicar activos.

No duplicar órdenes.

No crear una segunda tabla paralela de equipos.

==================================================
3. ACCESO AL PREOPERACIONAL
==================================================

El usuario debe poder iniciar un preoperacional desde:

A. Ficha del equipo

[ INICIAR PREOPERACIONAL ]

B. Lista de equipos

acción contextual:

[ Preoperacional ]

C. QR del equipo, si la capacidad QR existente lo permite.

D. Home, mediante:

[ Iniciar preoperacional ]

Si el usuario llega por QR:

QR
→ identificar activo
→ validar acceso
→ mostrar equipo
→ iniciar preoperacional.

No aceptar un activo arbitrario enviado desde frontend para saltarse autorización.

El backend debe validar el activo y el tenant mediante los mecanismos existentes.

Objetivo principal:

No mostrar una pantalla gigantesca con 50 campos simultáneamente.

Agrupar los ítems por categorías.

==================================================
5. PLANTILLAS
==================================================

Reutilizar Dynamic Forms si técnicamente corresponde.

Una plantilla de preoperacional debe permitir definir:

- nombre;
- descripción;
- tipo de equipo;
- categoría;
- versión;
- vigencia;
- ítems;
- orden;
- obligatoriedad;
- tipo de respuesta;
- severidad;
- evidencia requerida;
- observación requerida;
- comportamiento ante incumplimiento.

NO crear un constructor de formularios nuevo.

Si Dynamic Forms ya soporta estas capacidades, extenderlo mínimamente.

Si una capacidad no existe, documentar el GAP antes de inventar una arquitectura nueva.

==================================================
6. TIPOS DE RESPUESTA
==================================================

El checklist debe soportar, según las capacidades reales existentes:

✓ CUMPLE

✕ NO CUMPLE

⚠ OBSERVACIÓN

○ NO APLICA

Cuando el código existente utilice otra nomenclatura, mantener el contrato existente y mapearlo a esta experiencia visual.

No romper contratos existentes por razones exclusivamente visuales.

==================================================
7. REGLA DE EVIDENCIA
==================================================

NO obligar a tomar fotografías para absolutamente todo.

La evidencia debe solicitarse cuando:

- el ítem lo requiere;
- existe incumplimiento;
- existe una observación relevante;
- la plantilla lo establece.

Ejemplo:

✕ NIVEL DE ACEITE

Motivo:
[ Nivel bajo ]

Observación:
[________________]

Evidencia:
[ Tomar foto ]

[ Continuar ]

No bloquear innecesariamente al usuario cuando la evidencia no sea requerida.

==================================================
8. RESULTADO DEL PREOPERACIONAL
==================================================

Al finalizar debe existir un resultado operacional claro.

Estados:

🟢 APTO

🟡 APTO CON OBSERVACIONES

🔴 NO APTO

NO depender exclusivamente del color.

Siempre mostrar texto.

Ejemplo:

RESULTADO

🟡 APTO CON OBSERVACIONES

El equipo puede continuar operando.

2 observaciones requieren seguimiento.

[ VER OBSERVACIONES ]

o:

🔴 NO APTO

Se detectaron condiciones que impiden la operación.

1 hallazgo crítico.

[ VER HALLAZGOS ]

==================================================
9. REGLAS DE APTO / NO APTO
==================================================

Aplicar las decisiones de Dirección establecidas en LITE-02:

APTO:
Todos los requisitos obligatorios cumplen.

APTO CON OBSERVACIONES:
Existen observaciones que no impiden continuar operación.

NO APTO:
Existe una condición que impide continuar operación.

IMPORTANTE:

No inventar automáticamente qué ítems son críticos.

La criticidad debe provenir de:

- configuración existente;
- plantilla;
- catálogo;
- regla de negocio existente.

Si el código no tiene actualmente una fuente de verdad para determinar criticidad:

DETENER la implementación de esa parte y documentar GAP.

NO inventar reglas de seguridad.

==================================================
10. HALLAZGOS
==================================================

Cuando un ítem produzca un incumplimiento:

generar un hallazgo dentro del modelo existente si éste ya soporta la relación.

El hallazgo debe conservar procedencia:

PREOPERACIONAL
→ ACTIVO
→ ÍTEM
→ RESPUESTA
→ OBSERVACIÓN
→ EVIDENCIA

Debe ser posible saber:

- qué equipo;
- cuándo;
- quién realizó el preoperacional;
- qué ítem falló;
- qué respuesta dio;
- qué evidencia existe;
- qué severidad tiene.

NO generar todavía una OT automáticamente si eso pertenece a LITE-05.

Pero dejar preparada la procedencia para que LITE-05 pueda conectar:

HALLAZGO → OT

sin reconstruir la información.

==================================================
11. NO DUPLICAR HALLAZGOS
==================================================

Un usuario puede reintentar o refrescar una operación.

Debe respetarse la idempotencia existente.

No crear duplicados por:

- doble click;
- refresh;
- retry;
- pérdida temporal de conexión;
- reenvío del formulario.

Utilizar los mecanismos de idempotencia existentes.

Si el dominio actual no tiene una capacidad suficiente:

documentar el GAP antes de introducir una nueva solución.

==================================================
12. ESTADO DEL PREOPERACIONAL
==================================================

El proceso debe manejar estados apropiados según lo soportado actualmente:

- NO INICIADO
- EN PROGRESO
- COMPLETADO

Si existe capacidad de borrador/offline en Dynamic Forms, reutilizarla.

NO implementar una segunda cola offline.

IMPORTANTE:

El preoperacional puede necesitar ser realizado desde campo.

Si el sistema existente permite guardar progreso localmente de forma segura:

reutilizarlo.

Si no existe capacidad segura:

NO inventar sincronización offline en esta fase.

Documentar GAP.

Nunca marcar como completado algo que no haya sido sincronizado/persistido correctamente.

==================================================
13. FECHA Y HORA
==================================================

La ejecución debe conservar:

- fecha/hora de inicio;
- fecha/hora de finalización;
- usuario;
- activo;
- plantilla/versión utilizada.

No usar la hora enviada por el frontend como fuente de verdad cuando exista infraestructura server-side.

Usar las convenciones de tiempo existentes de DeltaOps.

==================================================
14. IDENTIDAD
==================================================

La ejecución debe registrar la identidad canónica.

Nunca confiar en:

- nombre enviado por frontend;
- identityId arbitrario;
- tenantId enviado por frontend.

Usar la sesión autenticada.

Respetar:

RBAC
RLS
tenant isolation
capacidades.

==================================================
15. CENTRO DE COSTOS
==================================================

El preoperacional debe mostrar el contexto del activo:

Centro de costos
Ubicación
Responsable
Equipo de mantenimiento

pero estas dimensiones siguen siendo independientes.

NO asumir:

Centro = ubicación.

Centro = responsable.

Centro = grupo.

Si alguna dimensión no está configurada:

mostrar:

—

o:

No configurado

Nunca inventar información.

==================================================
16. EQUIPOS DE MANTENIMIENTO
==================================================

La dirección estableció que los centros pueden tener estructuras diferentes.

Por tanto:

NO exigir un coordinador.

NO exigir un supervisor.

NO exigir separación universal entre:

asignar
ejecutar
revisar
aprobar.

En esta fase únicamente mostrar el contexto existente.

La segregación de funciones será utilizada en fases posteriores.

17. EXPERIENCIA DE USUARIO
==================================================

Aplicar el Design System existente.

Utilizar:

--do-*
Select
Button
Input
Toast
Modal
Card
Badge

etc.

NO crear un sistema visual paralelo.

Tema claro y oscuro deben funcionar.

Requisitos:

- contraste;
- botones táctiles;
- estados claramente diferenciados;
- focus;
- feedback;
- loading;
- errores;
- éxito;
- estados vacíos.

No depender únicamente de color.

==================================================
18. EXPERIENCIA DE ERROR
==================================================

Nunca mostrar errores técnicos como:

500
SQLSTATE
RLS
tenant_id
foreign key
UUID
stack trace

al usuario final.

Ejemplos:

En lugar de:

"401 Unauthorized"

usar:

"No pudimos validar tu sesión. Intenta nuevamente."

En lugar de:

"500 INTERNAL"

usar:

"No pudimos guardar el preoperacional. Tus respuestas no se han marcado como completadas."

==================================================
19. NO INVENTAR DATOS
==================================================

Esta regla es ABSOLUTA.

Si el tenant demo no tiene:

- plantillas;
- equipos;
- centros;
- responsables;
- checklists;

mostrar estado vacío.

Ejemplo:

"No hay plantillas de preoperacional configuradas."

NO crear datos ficticios automáticamente para mejorar una captura.

Si se requiere seed para pruebas:

debe estar claramente identificado como seed de pruebas y no alterar datos reales.

==================================================
20. SEGURIDAD
==================================================

No modificar RLS/RBAC.

No eliminar guards.

No aceptar tenantId del frontend.

No aceptar identityId del frontend.

No permitir ejecutar un preoperacional sobre un activo de otro tenant.

No permitir que un usuario consulte ejecuciones que no tiene autorización para consultar.

Backend = autoridad.

Frontend = experiencia.
