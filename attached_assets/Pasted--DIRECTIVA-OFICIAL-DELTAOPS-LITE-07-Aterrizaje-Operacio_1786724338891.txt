# DIRECTIVA OFICIAL — DELTAOPS LITE-07
# "Aterrizaje Operacional Delta: Equipo, Horómetro, Rutinas, Combustible, Mano de Obra y Hoja de Vida"

## CONTEXTO DE DIRECCIÓN

DeltaOps ya cuenta con las fases DGP-023.x y DELTAOPS LITE-01 a LITE-06 cerradas.

NO estamos construyendo nuevamente la plataforma.

NO debemos eliminar las capacidades robustas que ya existen.

El objetivo de esta fase es aterrizar DeltaOps Lite a la operación REAL de Delta Logística.

La plataforma actual está técnicamente avanzada, pero su experiencia todavía refleja demasiado un CMMS/EAM genérico.

La Dirección considera que la operación real debe girar principalmente alrededor de:

EQUIPO
→ HORÓMETRO / KILOMETRAJE
→ PREOPERACIONAL
→ OPERACIÓN
→ RUTINA DE MANTENIMIENTO
→ HALLAZGO / OT
→ EJECUCIÓN
→ HORAS HOMBRE
→ REPUESTOS / CONSUMOS
→ COMBUSTIBLE
→ CIERRE
→ HOJA DE VIDA
→ INDICADORES

La aplicación debe ser sencilla para el usuario operativo y conservar las capacidades administrativas/avanzadas detrás de una experiencia por perfil.

Esta fase debe analizar el proyecto real, la documentación existente y el material de negocio disponible antes de modificar cualquier código.

# 3. OBJETIVO REAL DE DELTAOPS LITE

El sistema debe dejar de sentirse como:

"un ERP con muchos módulos de mantenimiento"

y comenzar a sentirse como:

"la herramienta diaria para controlar los equipos y su mantenimiento".

El usuario debe poder pensar:

"Esta es mi máquina."

"Voy a revisar mi máquina."

"Mi máquina tiene una novedad."

"Esta máquina necesita mantenimiento."

"Voy a ejecutar el mantenimiento."

"Voy a registrar lo que hice."

"Voy a cerrar el trabajo."

Y el sistema debe encargarse de alimentar:

- hoja de vida;
- costos;
- horas hombre;
- combustible;
- utilización;
- mantenimiento preventivo;
- indicadores.

# 5. HORÓMETRO Y KILOMETRAJE

Este punto es CRÍTICO.

Analizar las capacidades actuales de:

- lecturas;
- horómetro;
- kilometraje;
- mantenimiento preventivo por uso;
- historial del activo.

El sistema debe considerar que el horómetro es una lectura acumulativa y monotónica.

No permitir silenciosamente:

1000 h → 900 h

Si existe corrección:

debe existir mecanismo de corrección/compensación auditada.

No inventar lecturas.

## Experiencia objetivo

Ejemplo:

EQUIPO: CARGADOR C5

Horómetro actual:
1.185 h

Próxima rutina:
1.200 h

Faltan:
15 h

Cuando se alcance la condición:

🔧 MANTENIMIENTO DE 1.200 h

[Iniciar mantenimiento]

La experiencia debe priorizar el disparador por uso cuando el equipo utilice horómetro.

Para vehículos:

usar kilometraje cuando corresponda.

Para otros activos:

usar el medidor configurado.

No asumir que todos los activos utilizan horómetro.

---

# 6. RUTINAS VS PLANES

La Dirección establece una diferencia importante:

Los centros de trabajo no necesariamente tienen un "líder de mantenimiento" o "planeador de mantenimiento".

Por lo tanto:

NO diseñar la experiencia alrededor de que una persona deba entrar periódicamente a:

"crear plan"
"programar plan"
"asignar plan"

para que el mantenimiento ocurra.

Las RUTINAS deben ser la fuente operacional.

El sistema debe respetar:

- frecuencia por horas;
- frecuencia por kilometraje;
- frecuencia por tiempo cuando aplique;
- tolerancias;
- última ejecución;
- próxima ejecución;
- vencimiento.

La rutina debe disparar la necesidad de mantenimiento.

La asignación y ejecución deben depender de las capacidades disponibles en el centro/operación.

El sistema NO debe exigir un coordinador de mantenimiento universal.

# 10. COMBUSTIBLE

Analizar la funcionalidad actual y los documentos empresariales relacionados con combustible.

El combustible debe convertirse en una experiencia asociada al activo, NO simplemente en un módulo aislado.

Registrar como mínimo según disponibilidad real:

- fecha;
- hora;
- equipo;
- tipo de combustible/energía;
- cantidad;
- unidad;
- horómetro o kilometraje;
- centro de trabajo;
- responsable;
- proveedor, si aplica;
- número de ticket/evidencia, si aplica.

IMPORTANTE:

NO asumir ACPM como único combustible.

La arquitectura existente contempla múltiples fuentes de energía.

El sistema debe permitir el combustible correspondiente al activo.

---

# 11. PROVEEDOR DE COMBUSTIBLE

La Dirección hace la siguiente observación de negocio:

Un mismo repuesto o combustible puede comprarse a diferentes proveedores en diferentes momentos.

Por lo tanto, NO convertir el registro de una operación sencilla en un proceso administrativo pesado.

Analizar si para DeltaOps Lite resulta más adecuado:

- proveedor opcional;
- nombre del proveedor;
- identificación/NIT;
- datos mínimos de la transacción;

sin obligar al usuario a crear previamente un maestro completo de proveedores.

Si el dominio actual exige proveedor maestro, NO modificarlo en esta fase.

Documentar una recomendación de UX:

"Proveedor como dato de transacción / snapshot"

y dejar la administración completa de proveedores como capacidad administrativa.

NO eliminar el módulo existente.

---

# 12. RENDIMIENTO DE COMBUSTIBLE

NO permitir que el usuario digite manualmente:

"rendimiento = 5 gal/h"

El rendimiento debe derivarse de:

consumo
+
lecturas del activo
+
intervalo de uso.

Ejemplos:

gal/h
km/gal
kWh/km

según tipo de activo/energía.

Si no existen datos suficientes:

mostrar:

"Sin datos suficientes para calcular rendimiento"

NO inventar indicadores.

# 14. HORAS HOMBRE

Analizar la implementación existente.

Las horas hombre deben estar relacionadas con:

- técnico/persona;
- activo;
- OT;

- hora final;
- duración;

08:10

11:20

Juan Pérez

Guardar y asociar a la OT y al activo.

# 21. REDISEÑO VISUAL Y RESPONSIVE

La Dirección considera que la UI actual todavía presenta problemas importantes:

- contenido demasiado comprimido;
- exceso de espacio lateral;
- navegación superior demasiado cargada;
- problemas de responsive;
- elementos que no encajan correctamente;
- mala adaptación móvil;

- problemas de contraste;
- textos pequeños;

Esto debe tratarse como un problema de experiencia, no como una simple corrección CSS.

Diseñar:

## Desktop

Uso eficiente del ancho.

Contenido centrado pero con max-width razonable.

No dejar grandes espacios vacíos innecesarios.

## Tablet

Reorganización de navegación y contenido.

## Móvil

Experiencia diseñada específicamente para operación.

No simplemente reducir columnas.

Acciones táctiles grandes.

Prioridad:

1. Acción principal.
2. Estado.
3. Información crítica.
4. Evidencia.
5. Información secundaria.
