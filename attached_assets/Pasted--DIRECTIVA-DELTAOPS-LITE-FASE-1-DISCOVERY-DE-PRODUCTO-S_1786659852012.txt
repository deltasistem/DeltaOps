# DIRECTIVA DELTAOPS LITE — FASE 1
## DISCOVERY DE PRODUCTO, SIMPLIFICACIÓN OPERACIONAL Y AUDITORÍA UX/UI

Rol:
Actúa como Product Architect, UX/UI Lead y Software Architect de DeltaOps.

IMPORTANTE:
Esta fase NO es una implementación.
NO modificar código.
NO modificar base de datos.
NO crear migraciones.
NO modificar contratos API.
NO modificar RBAC/RLS.
NO eliminar módulos.
NO eliminar funcionalidades.
NO cambiar arquitectura.
NO ejecutar refactors.

El objetivo de esta fase es entender el producto actual y diseñar una propuesta concreta para convertir DeltaOps en una experiencia mucho más simple, agradable y orientada a la operación real de Delta Logística.

---

## 1. CONTEXTO DEL PROGRAMA

DeltaOps ya posee un core funcional y arquitectónicamente robusto construido mediante las fases DGP anteriores.

Actualmente existen capacidades relacionadas con:

- Activos
- Órdenes de trabajo
- Inventario
- Planes
- Preventivo
- Correctivo
- Abastecimiento
- Utilización
- Mano de obra
- Costos
- Analytics
- Identidad
- RBAC
- RLS
- Sesiones
- Auditoría
- Integraciones
- Centro Operacional

Estas capacidades NO deben eliminarse.

El objetivo ahora es cambiar la experiencia del usuario.

La aplicación debe dejar de sentirse como una colección de módulos técnicos y convertirse en una plataforma operacional de mantenimiento.

---

# 2. OBJETIVO DE DELTAOPS LITE

"Lite" NO significa eliminar el core.

Significa:

CORE ROBUSTO
+
EXPERIENCIA SIMPLE

La complejidad debe permanecer en backend, dominio, seguridad y datos cuando sea necesaria.

La interfaz debe mostrar solamente lo que cada usuario necesita para realizar su trabajo.

Principio rector:

"El usuario no debe necesitar conocer la arquitectura de DeltaOps para poder utilizar DeltaOps."

# 6. TEMA CLARO Y OSCURO

Audita específicamente el sistema de temas.

Debe existir conceptualmente:

ThemeProvider
    ↓
design tokens
    ↓
todos los componentes

No debe existir una colección de estilos independientes para cada pantalla.

Identifica:

- colores de fondo
- texto principal
- texto secundario
- bordes
- inputs
- selects
- botones
- tablas
- badges
- estados
- iconos
- logos
- focus states
- hover states

Verifica específicamente que:

- el logo sea legible en ambos temas;
- los textos tengan contraste suficiente;
- los `<select>` y opciones sean utilizables en oscuro;
- los estados no dependan únicamente del color;
- los componentes mantengan consistencia entre temas.

El logo blanco/oficial para fondo oscuro debe considerarse parte del sistema de identidad visual existente.

No inventes una nueva identidad de marca.

---

# 7. PROPUESTA DE NAVEGACIÓN

Diseña una propuesta de navegación mucho más pequeña.

No elimines funcionalidades.

Determina qué debería aparecer en la navegación principal y qué debería quedar agrupado.

Como referencia conceptual, evalúa una estructura similar a:

INICIO
MANTENIMIENTO
EQUIPOS
PREOPERACIONAL
INVENTARIO
INDICADORES
ADMINISTRACIÓN

Pero NO la adoptes automáticamente.

Determina la mejor estructura basándote en el código real y los roles existentes.

La navegación debe ser diferente según el rol cuando esto tenga sentido.

Un técnico NO debería ver opciones administrativas.

Un operador NO debería ver configuración técnica.

Un administrador puede acceder al conjunto completo.

# 9. PREOPERACIONAL

Analiza especialmente esta funcionalidad porque será uno de los ejes de DeltaOps Lite.

Determina cómo debería funcionar:

Seleccionar equipo
→ iniciar preoperacional
→ mostrar checklist
→ responder condiciones
→ evidenciar incumplimiento
→ registrar observación
→ determinar APTO / NO APTO

Si una condición crítica falla:

→ generar automáticamente una novedad/incidencia
→ permitir generar OT según reglas definidas
→ asociar automáticamente:
   equipo
   operador
   fecha/hora
   checklist
   hallazgo

No implementar.

Solo diseñar el flujo funcional y señalar qué capacidades existentes pueden reutilizarse.

# 11. REGLA FUNDAMENTAL: NO DUPLICAR FUNCIONALIDAD

Antes de proponer cualquier pantalla nueva:

Buscar si la funcionalidad ya existe.

Si existe:
→ reutilizarla.

Si existe parcialmente:
→ proponer composición.

Si no existe:
→ marcar como GAP.

No crear módulos paralelos.

No crear una segunda versión de Órdenes, Activos, Inventario, etc.

# 13. PROPUESTA VISUAL

Sin implementar todavía, propón un lenguaje visual para DeltaOps Lite:

- corporativo
- moderno
- limpio
- industrial
- profesional
- fácil de utilizar
- mobile-first para operación

Evitar:

- exceso de tarjetas
- exceso de bordes
- dashboards saturados
- colores innecesarios
- sombras exageradas
- gradientes decorativos excesivos
- interfaces que parezcan un ERP genérico

Priorizar:

- jerarquía
- acciones claras
- estados visibles
- información contextual
- botones grandes para operación móvil
- formularios simples
- feedback inmediato
- consistencia visual

No crear un diseño experimental.
