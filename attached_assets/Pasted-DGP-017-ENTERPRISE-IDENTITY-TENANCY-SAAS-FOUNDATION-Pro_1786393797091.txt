DGP-017 — ENTERPRISE IDENTITY, TENANCY & SAAS FOUNDATION

Programa DeltaOps

INSTRUCCIÓN DE EJECUCIÓN

Implementa DGP-017 como una fase formal del programa DeltaOps.

ANTES DE ESCRIBIR CÓDIGO:
1. Lee y comprende todo el corpus existente del proyecto.
2. Respeta estrictamente ETS-001…012, Engineering Charter, ESI-001…010 y todos los DGP cerrados hasta DGP-016.
3. Revisa especialmente Kernel, Shared Platform, Business Foundation, Workflow Engine, Dynamic Forms, Design System, API Server, Activos, Órdenes, Inventario, Planes, Abastecimiento, Preventivo, Correctivo, Ecosistema de Mantenimiento y Analytics.
4. Identifica los contratos existentes de autenticación, sesión, tenant, autorización, capacidades, permisos, configuración, auditoría, notificaciones y usuarios antes de crear cualquier pieza nueva.
5. NO reemplaces infraestructura existente si puede extenderse de forma compatible.
6. NO modifiques contratos congelados salvo que sea estrictamente necesario y, en ese caso, la extensión debe ser aditiva, compatible y documentada.
7. No inventes una segunda arquitectura de autenticación, autorización o multitenancy.
8. No construyas módulos de negocio nuevos en esta fase.
9. No construyas BI, IA, reportes ni analítica nueva.
10. No introduzcas componentes visuales fuera del Design System DGP-005.

OBJETIVO

Convertir DeltaOps de una plataforma técnica con Tenant DEMO y usuarios de demostración en una verdadera base Enterprise SaaS multiempresa, preparada para operar como servicio para múltiples compañías independientes.

La plataforma debe permitir:

EMPRESA/TENANT
→ configuración propia
→ usuarios propios
→ roles propios
→ permisos/capacidades
→ branding configurable
→ acceso aislado
→ módulos habilitados
→ auditoría
→ notificaciones
→ administración

La regla fundamental es:

NINGÚN USUARIO DE UN TENANT PUEDE VER, CONSULTAR, MODIFICAR, BUSCAR, EXPORTAR, RECIBIR NI INFERIR INFORMACIÓN DE OTRO TENANT.

El aislamiento debe existir en backend, sesión, autorización, consultas, escrituras, sincronización, cachés, almacenamiento lógico y experiencia.

1. IDENTITY & AUTHENTICATION FOUNDATION
==================================================

Construye la base oficial de identidad de DeltaOps reutilizando la infraestructura existente siempre que sea posible.

Debe existir:

- Usuario
- Identidad
- Sesión
- Tenant
- Estado de usuario
- Estado de sesión
- fecha de creación
- último acceso
- configuración básica
- auditoría

Implementa autenticación segura y preparada para producción.

El login debe permitir:

- correo electrónico
- contraseña
- validación de credenciales
- creación de sesión
- expiración de sesión
- cierre de sesión
- renovación segura cuando corresponda
- protección contra sesiones inválidas
- aislamiento por tenant
- manejo de usuario deshabilitado
- manejo de tenant deshabilitado

NO almacenar contraseñas en texto plano.

Usar hash seguro existente en el stack; si no existe una implementación adecuada, incorporar una solución estándar y documentada.

NO colocar credenciales reales en documentación, código fuente, fixtures ni repositorio.

El usuario debe entrar únicamente al tenant al que pertenece según la relación oficial de identidad.

3. PASSWORD RECOVERY
==================================================

Implementa recuperación de acceso preparada para producción.

Flujo:

Solicitar recuperación
→ validar identidad
→ generar token seguro y temporal
→ enviar correo
→ abrir enlace
→ validar token
→ establecer nueva contraseña
→ invalidar token
→ registrar auditoría

El token:

- debe ser de un solo uso
- debe expirar
- no debe almacenarse en texto plano si la arquitectura lo permite
- debe estar asociado al usuario correcto
- debe estar aislado por tenant
- no debe permitir enumeración de usuarios

La respuesta pública del endpoint debe evitar revelar si un correo existe o no.

SUSPENDIDO

El sistema debe impedir acceso cruzado entre tenants.

==================================================
5. USUARIOS MULTIEMPRESA
==================================================

Modela correctamente la relación Usuario ↔ Tenant.

No asumir que un usuario necesariamente debe pertenecer para siempre a un solo tenant si la arquitectura SaaS futura puede beneficiarse de una identidad global.

Diseña la frontera de identidad de forma que pueda soportar:

Usuario
→ Identidad global
→ Membresía Tenant
→ Roles
→ Permisos

Sin embargo, la sesión activa debe tener siempre un tenant-context explícito.

Si el usuario pertenece a múltiples tenants:

- debe poder seleccionar el tenant al iniciar sesión
- debe poder cambiar de tenant únicamente mediante un flujo seguro
- cada cambio debe renovar/validar el contexto de autorización
- nunca reutilizar permisos del tenant anterior
- cachés y datos deben quedar aislados

Si el usuario solo pertenece a un tenant, el acceso debe ser directo.

El rol debe componer permisos/capacidades.

No utilizar:

disperso por la aplicación.

Usar AuthorizationRuntime / permisos / capacidades existentes.
