==================================================
1. OBJETIVO
==================================================

Resolver G-1 de forma arquitectónicamente correcta.

Una Orden de Trabajo debe poder identificar de manera inequívoca al responsable/técnico asignado mediante la identidad canónica de DeltaOps.

Debe existir una relación fuerte:

OT
↓
identityId
↓
idn_identities / identidad canónica

El objetivo NO es crear un nuevo sistema de usuarios.

El objetivo NO es importar usuarios de Microsoft 365.

El objetivo NO es modificar el modelo de autenticación.

El objetivo es que Órdenes pueda decir:

"Esta OT está asignada a esta identidad DeltaOps."

==================================================
2. PRINCIPIO FUNDAMENTAL
==================================================

IDENTIDAD DELTAOPS ES LA ÚNICA FUENTE DE VERDAD.

No utilizar:

- Microsoft Entra ID;
- Microsoft Graph;
- correo electrónico como identificador;
- nombre del usuario;
- texto libre;
- username como clave de negocio.

El identificador canónico debe ser `identityId` o el identificador equivalente ya definido por el contrato de identidad.

No inventar otro identificador.

==================================================
3. AUDITAR PRIMERO
==================================================

Antes de modificar el código, inspeccionar el corpus real y determinar:

- estructura actual de `asignado_id`;
- dónde se escribe;
- dónde se lee;
- qué comandos lo reciben;
- qué read models lo exponen;
- qué frontend lo utiliza;
- qué tests dependen de él;
- qué rutas lo utilizan;

- cómo se resuelve actualmente la identidad autenticada.

No asumir.

Documentar exactamente qué componentes serán afectados.

Si existe un patrón canónico de referencia a identidad en otro módulo, reutilizarlo.

No crear un patrón paralelo.

==================================================
4. PUERTO DE IDENTIDAD
==================================================

Si el módulo Órdenes necesita consultar identidad para validar una asignación:

crear o utilizar el mecanismo arquitectónico mínimo necesario.

Preferencia:

Órdenes
→ puerto/adaptador de identidad
→ identidad canónica

No permitir:

Órdenes
→ acceso directo a tablas internas de identidad

si eso viola las reglas arquitectónicas existentes.

Si ya existe un puerto de identidad reutilizable:

UTILIZARLO.

No duplicarlo.

==================================================
5. MODELO DE ASIGNACIÓN
==================================================

La asignación debe quedar representada con un identificador canónico.

Evaluar la mejor solución entre:

A. reemplazar `asignado_id`;

B. introducir `asignado_identity_id`;

C. mantener compatibilidad temporal y agregar el nuevo campo.

Elegir según el contrato real existente y justificar la decisión.

No romper consumidores innecesariamente.

La solución final debe evitar que una OT pueda quedar asignada únicamente mediante texto libre.

==================================================
6. VALIDACIÓN
==================================================

Al asignar una OT:

1. Obtener identidad canónica.
2. Verificar que existe.
3. Verificar que está activa.
4. Verificar que pertenece al tenant correcto.
5. Verificar que tiene las condiciones/capacidades necesarias para ser asignada según las reglas actuales.
6. Persistir `identityId`.

Nunca confiar en un `tenantId` enviado desde frontend.

El tenant debe derivarse del contexto autenticado/backend.

==================================================
7. TENANT ISOLATION
==================================================

CRÍTICO.

No permitir:

Tenant A
→ asignar OT
→ identidad perteneciente a Tenant B.

La validación debe comprobar pertenencia de la identidad al mismo tenant de la OT.

Debe existir una prueba explícita de este escenario.
