DIRECTIVA DE DIRECCIÓN — DGP-020.3
FUNDACIÓN DE MANO DE OBRA

Programa DeltaOps

==================================================
ESTADO DEL PROGRAMA
==================================================

DGP-020 — Discovery: CERRADO / PASS
DGP-020.1 — Identidad en asignación: CERRADO / PASS
DGP-020.2 — Sesiones y duración real: CERRADO / PASS

La cadena operacional actualmente disponible es:

OT
→ identityId
→ activoId
→ sesión de trabajo
→ tramos append-only
→ tiempo efectivo

DGP-020.3 queda AUTORIZADO.

==================================================
1. OBJETIVO
==================================================

Construir la FUNDACIÓN DE MANO DE OBRA de DeltaOps.

El objetivo es poder determinar de forma auditable:

- quién realizó el trabajo;
- sobre qué OT;
- sobre qué activo;
- cuánto tiempo efectivo trabajó;
- qué unidad de mano de obra aplica;
- qué tarifa corresponde, si existe;
- qué costo de mano de obra puede derivarse;
- en qué tenant ocurrió;
- cuándo fue registrado;
- cuál es la fuente del tiempo.

La información debe quedar preparada para DGP-021 — Costos de Mantenimiento.

IMPORTANTE:

DGP-020.3 NO es todavía el módulo completo de costos.

No implementar contabilidad, facturación, presupuestos ni costos financieros generales.

==================================================
2. PRINCIPIO FUNDAMENTAL
==================================================

La fuente de verdad del TIEMPO DE MANO DE OBRA será:

SESIONES DE TRABAJO DE DGP-020.2

Por tanto:

OT
→ identityId
→ sesión
→ tiempo efectivo

No reconstruir horas desde:

- fecha de creación de OT;
- fecha de cierre;
- Workflow;
- Timeline;
- bitácora;
- timestamps de servidor;
- estimaciones.

El tiempo efectivo persistido por las sesiones es la fuente operacional.

==================================================
3. NO DUPLICAR EL CONCEPTO DE TIEMPO
==================================================

NO crear otra entidad que almacene:

"horas trabajadas"

si eso duplica el tiempo efectivo de DGP-020.2.

La mano de obra debe referenciar/componer:

- sesión;
- tiempo efectivo;
- identidad;
- OT;
- activo.

Si se necesita un snapshot para auditoría o costos históricos, documentarlo explícitamente y no convertirlo en una segunda fuente de verdad.

==================================================
4. CONCEPTO DE RECURSO HUMANO
==================================================

Evaluar la necesidad de una entidad/read model de recurso humano de mantenimiento.

Debe utilizar identidad canónica:

identityId

Nunca:

- nombre como identificador;
- correo como identificador;
- usuario legacy;
- documento como FK.

La identidad debe provenir del servicio/puerto canónico existente.

No acceder directamente a tablas `idn_*`.

==================================================
5. PERFIL OPERACIONAL
==================================================

Determinar qué atributos son realmente necesarios para mano de obra.

Como mínimo evaluar:

- identityId;
- tenant;
- nombre de presentación;
- rol/capacidad;
- estado;
- categoría de mano de obra;
- unidad de costo;
- tarifa;
- vigencia.

No agregar atributos que el corpus no soporte sin declarar GAP.

==================================================
6. CATEGORÍA DE MANO DE OBRA
==================================================

Necesitamos poder diferenciar, si el contrato lo permite:

Ejemplo:

- Técnico mecánico;
- Técnico eléctrico;
- Soldador;
- Operador;
- Supervisor;
- Ayudante;
- Especialista.

PERO:

No inventar el catálogo definitivo.

Si actualmente no existe catálogo de categorías de mano de obra:

crear el contrato mínimo necesario o declarar el GAP correspondiente.

La categoría debe ser un concepto estable, no texto libre en cada OT.

==================================================
7. UNIDAD DE TARIFA
==================================================

Evaluar explícitamente la unidad de tarifa.

Ejemplos posibles:

- hora;
- jornada;
- turno.

La recomendación de Dirección para esta fase:

PRIMERA UNIDAD SOPORTADA:

HORA

No implementar jornada/turno hasta que exista contrato real que lo justifique.

La tarifa debe poder expresarse como:

COP / hora

sin asumir otra moneda.

Si el sistema ya posee configuración monetaria por tenant:

reutilizarla.

No crear un sistema monetario paralelo.

==================================================
8. TARIFA
==================================================

La tarifa debe ser versionable.

No sobrescribir una tarifa histórica que ya haya sido utilizada.

Modelo conceptual:

Tarifa:
- identity/categoría;
- valor;
- moneda;
- unidad;
- vigenciaDesde;
- vigenciaHasta;
- tenant;
- estado;
- auditoría.

Si el corpus actual no permite determinar si la tarifa pertenece a:

PERSONA
o
CATEGORÍA

detenerse en ese punto de diseño y documentar la decisión.

La arquitectura debe soportar posteriormente la evolución sin romper costos históricos.

==================================================
9. COSTO DE MANO DE OBRA
==================================================

El costo operacional futuro debe poder derivarse:

TIEMPO EFECTIVO
×
TARIFA VIGENTE

Ejemplo:

2.5 horas
×
$35.000 COP/hora

=
$87.500 COP

PERO:

No redondear ni alterar el tiempo de la sesión.

Definir explícitamente política de precisión monetaria.

No usar floating point para dinero si la arquitectura existente utiliza decimal/numeric.

Reutilizar la convención monetaria existente.

==================================================
10. SNAPSHOT HISTÓRICO
==================================================

Este punto es CRÍTICO.

Si mañana una tarifa cambia:

$35.000/h
→
$40.000/h

una OT cerrada ayer no puede cambiar su costo histórico automáticamente.

Por tanto, evaluar un snapshot auditable de:

- tarifa aplicada;
- moneda;
- unidad;
- identidad/categoría;
- tiempo utilizado;
- cálculo resultante.

La fuente de verdad del tiempo continúa siendo DGP-020.2.

El snapshot únicamente preserva la valoración histórica utilizada.

==================================================
11. ESTADO DEL RECURSO
==================================================

Evaluar estados mínimos:

ACTIVO
INACTIVO

No permitir que un recurso inactivo sea seleccionado para nuevas operaciones si el contrato lo exige.

No eliminar físicamente históricos.

La identidad canónica sigue existiendo aunque cambie el estado operacional.

==================================================
12. RELACIÓN CON OT
==================================================

La mano de obra debe quedar relacionada con:

tenant
+
OT
+
identityId
+
sesión
+
activoId

El activo debe derivarse de la OT/sesión.

No aceptar un activo arbitrario desde frontend.

No crear una segunda relación OT-Activo.

==================================================
13. RELACIÓN CON SESIONES

Una sesión cerrada proporciona:

identityId
OT
activoId
tiempo efectivo

La mano de obra debe consumir esa información.

No permitir que frontend envíe:

"trabajé 8 horas"

como fuente de verdad.

El frontend puede mostrar datos.

El backend debe derivarlos de las sesiones.

==================================================
14. SESIONES ABIERTAS

No valorar definitivamente una sesión abierta como costo final.

Puede mostrarse:

"costo estimado"

si el contrato lo permite.

Pero debe diferenciarse claramente:

COSTO ESTIMADO
vs
COSTO FINAL

Una sesión cerrada puede producir valoración definitiva.

No inventar costos para sesiones sin tarifa.

==================================================
15. AUSENCIA DE TARIFA

Si existe tiempo efectivo pero no existe tarifa:

NO asumir cero.

NO ocultar el problema.

Mostrar/registrar:

"Tarifa no configurada"

y permitir que el dato operacional exista sin inventar un costo.

Esto es especialmente importante:

SIN TARIFA ≠ COSTO $0

==================================================
16. CAMBIO DE TARIFA

Definir comportamiento cuando una tarifa cambia mientras una sesión está abierta.

La recomendación inicial:

La valoración histórica debe utilizar la política de vigencia definida por el contrato.

No aplicar automáticamente una nueva tarifa a tiempo trabajado antes de su vigencia.

Si el tiempo de una sesión cruza dos períodos tarifarios:

NO inventar una política.

Documentar el GAP si no existe contrato.

21. RLS
==================================================

Todas las entidades nuevas deben estar protegidas por RLS.

Probar:

Tenant A
→ no ve mano de obra de Tenant B.

Identidad A
→ no ve información privada de Tenant B.

Supervisor A
→ solo tenant A.

==================================================
22. RBAC
==================================================

No inventar permisos si no son necesarios.

Utilizar capacidades existentes.

Como mínimo evaluar:

TENANT_ADMIN
→ administración y consulta según contrato.

SUPERVISOR
→ consulta/gestión según capacidades.

PLANIFICADOR
→ consulta según contrato.

TECNICO
→ consulta de su propia mano de obra y sesiones.

CONSULTA
→ solo lectura.

No permitir que CONSULTA:

- cree;
- modifique;
- elimine;
- configure tarifas.

==================================================
23. TARIFAS — SEGURIDAD

La configuración de tarifas debe ser una operación administrativa.

Un técnico NO puede modificar su propia tarifa.

Un usuario NO puede alterar una tarifa para modificar retroactivamente un costo.

Todo cambio debe ser auditable.

==================================================

==================================================
25. IDEMPOTENCIA

Toda mutación nueva debe utilizar:

opId

y el patrón durable existente.

No aceptar doble creación de:

- tarifa;
- recurso;
- valoración.

==================================================
26. OFFLINE

No crear una segunda cola.

Las sesiones continúan siendo la fuente de tiempo.

Si la valoración de mano de obra depende de información que solo existe online:

la operación offline debe conservar el hecho y calcular posteriormente al sincronizar.

No inventar tarifas offline si no están disponibles.

==================================================
27. DINERO

CRÍTICO:

Usar la representación monetaria existente del proyecto.

No usar:

JavaScript floating point

para cálculos monetarios persistidos.

Utilizar:

numeric/decimal
o
la abstracción monetaria existente.

Definir precisión y redondeo.

Documentar:

- precisión interna;
- redondeo;
- momento del redondeo.

Nunca redondear el tiempo efectivo para calcular el costo.

==================================================

COP es configuración inicial,

==================================================

"horas trabajadas".

Debe poder responderse con evidencia:

¿Quién trabajó?
¿En qué OT?
¿Sobre qué activo?
¿Cuánto tiempo efectivo trabajó?
¿Qué tarifa aplicaba?
¿Por qué esa tarifa?
¿Desde cuándo estaba vigente?
