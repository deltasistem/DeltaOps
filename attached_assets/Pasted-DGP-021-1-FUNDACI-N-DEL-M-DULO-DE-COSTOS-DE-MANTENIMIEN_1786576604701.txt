DGP-021.1 — FUNDACIÓN DEL MÓDULO DE COSTOS DE MANTENIMIENTO

DIRECTIVA DE DIRECCIÓN

DGP-021 Discovery = PASS.
DGP-021.0 = PASS.
GAP-COST-14 = RESUELTO.

Ahora se autoriza implementar únicamente la FUNDACIÓN del módulo de Costos de Mantenimiento.

NO implementar todavía la composición completa de costos de OT/Activo.

==================================================
1. OBJETIVO
==================================================

Crear una base económica auditable y multitenant para DeltaOps que permita materializar hechos económicos de mantenimiento sin duplicar las fuentes de verdad existentes.

La fundación debe quedar preparada para consumir posteriormente:

- Mano de obra de DGP-020.3.
- Repuestos/materiales mediante DGP-021.0.
- Combustible de DGP-019.
- Otros costos futuros.

IMPORTANTE:

DGP-021.1 NO debe calcular todavía el costo total de una OT ni el costo total de un activo.

Solo debe construir la infraestructura necesaria para registrar y consultar hechos económicos de forma auditable.

==================================================
2. PRINCIPIO DE ARQUITECTURA
==================================================

La fuente de verdad de cada componente continúa perteneciendo a su módulo de origen.

Ejemplo:

Mano de obra
→ module-manodeobra

Combustible
→ module-utilizacion

Costo de materiales
→ module-abastecimiento

module-costos NO debe duplicar esas fuentes.

Debe materializar únicamente el hecho económico necesario para conservar:

- qué ocurrió;
- cuánto;
- cuándo;
- sobre qué OT;
- sobre qué activo;
- con qué moneda;
- con qué fuente;
- con qué snapshot;
- y cuál fue el estado del hecho.

==================================================
7. SNAPSHOT ECONÓMICO
==================================================

Este es uno de los puntos más importantes.

Cuando un hecho económico se materializa, debe conservar la información necesaria para que cambios posteriores en la fuente no modifiquen el histórico.

Ejemplo:

Material:
costo promedio ponderado actual = 35.000,123456

Se crea un hecho económico.

Posteriormente el costo promedio cambia a 42.000.

El hecho histórico debe continuar representando:

35.000,123456

No debe recalcularse automáticamente.

La misma regla aplica a:

- tarifas;
- combustible;
- cantidades;
- moneda;
- unidad;
- categoría.

No modificar históricos mediante referencias vivas.

==================================================
8. DINERO
==================================================

REGLA ABSOLUTA:

Dinero = decimal string-safe.

Nunca:

parseFloat
Number
float
conversiones implícitas.

Mantener:

PostgreSQL numeric
→ driver string
→ dominio string
→ API string
→ frontend string.

Aplicar el mismo estándar utilizado por DGP-020.3 y DGP-021.0.

No introducir una precisión distinta sin justificación.

==================================================
9. MONEDA
==================================================

No convertir monedas.

Los hechos deben conservar su moneda.

Los agregados futuros deberán separar:

COP
USD
CLP
etc.

Nunca sumar:

100.000 COP + 100 USD

como si fueran comparables.

Si una consulta encuentra múltiples monedas:

devolverlas separadamente.

==================================================
10. ESTADOS
==================================================

Definir únicamente estados necesarios y justificables.

Como mínimo evaluar:

ACTIVO
ANULADO

justificarlos antes de implementarlos.

La anulación debe ser auditable.

NO borrar hechos económicos.

NO editar silenciosamente un hecho histórico.

==================================================
11. INMUTABILIDAD
==================================================

Una vez materializado un hecho económico:

NO sobrescribir silenciosamente:

- costo;
- moneda;
- cantidad;
- fuente;
- OT;
- activo;
- snapshot.

Si existe un error:

utilizar mecanismo de corrección/anulación auditable.

Seguir el patrón append-only donde corresponda.

==================================================
12. IDENTIDAD
==================================================

Cuando un hecho requiera persona:

usar exclusivamente identityId canónico.

Nunca:

- email como ID;
- nombre como ID;
- usuario legacy;
- ID espejo.

Identity debe derivarse del contexto autenticado o de contratos públicos.

==================================================
13. OT Y ACTIVO
==================================================

Cuando el hecho provenga de una OT:

OT debe ser referencia verificable.

Cuando el activo provenga de una OT:

activoId debe derivarse de la OT cuando el contrato lo permita.

NO aceptar activoId arbitrario enviado por frontend si existe una relación canónica OT→Activo.

No duplicar la relación OT→Activo.

==================================================
14. MULTITENANCY
==================================================

tenantId exclusivamente desde contexto autenticado.

RLS obligatoria.

Todo hecho debe estar tenant-scoped.

Probar:

Tenant A no puede:

- crear hecho para Tenant B;
- consultar hecho de Tenant B;
- modificar hecho de Tenant B;
- anular hecho de Tenant B.

==================================================
15. RBAC
==================================================

No crear permisos nuevos innecesariamente.

Definir la matriz usando capacidades existentes cuando sea posible.

Evaluar como mínimo:

SUPER_ADMIN
TENANT_ADMIN
SUPERVISOR
PLANIFICADOR
TECNICO
CONSULTA

Separar:

- consulta;
- materialización;
- anulación;
- administración.

Un TECNICO no debe obtener capacidad administrativa sobre costos por el simple hecho de poder ejecutar una OT.

==================================================
16. IDEMPOTENCIA
==================================================

Toda materialización mutante debe tener:

opId

y claim durable.

El claim debe ejecutarse antes de producir efectos.

Doble solicitud con mismo opId:

exactamente un hecho.

Probar concurrencia real contra PostgreSQL.

==================================================

Ejemplos conceptuales:

MANO_DE_OBRA
→ module-manodeobra

MATERIAL
→ module-abastecimiento

COMBUSTIBLE
→ module-utilizacion

No depender únicamente de texto libre.

19. ORQUESTACIÓN

- fail-safe;
- idempotente;
- auditable;
- recuperable.

Un fallo en la materialización económica NO debe romper la operación principal cuando el flujo de negocio ya fue diseñado como fail-safe.

Pero el hecho pendiente debe quedar visible y recuperable.
