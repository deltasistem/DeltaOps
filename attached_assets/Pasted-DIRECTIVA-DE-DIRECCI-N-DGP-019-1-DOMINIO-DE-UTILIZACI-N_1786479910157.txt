==================================================
OBJETIVO
==================================================

Crear el nuevo módulo:

module-utilizacion

Su responsabilidad será proporcionar la fundación operacional para registrar:

1. Lecturas históricas de medidores.
2. Horómetro.
3. Odómetro/kilometraje.
4. Tanqueos/combustible.
5. Eventos operacionales relacionados con utilización cuando exista una fuente real.

El módulo debe quedar preparado para que posteriormente DeltaOps pueda calcular:

- consumo;
- L/h;
- L/100 km;
- costo por hora;
- costo por km;
- utilización;
- disponibilidad;
- tendencias;
- comportamiento histórico.

NO construir todavía dashboards ejecutivos.

NO implementar inteligencia predictiva.

NO implementar IA.

==================================================
1. MEDIDORES
==================================================

Implementar una entidad de historial de lecturas de medidores.

Como mínimo:

- id
- tenantId
- activoId
- tipoMedidor
- valor
- unidad
- fechaHora
- identityId / usuario
- origen
- evidencia si el contrato existente lo permite
- opId
- estado
- createdAt

Tipos iniciales:

HOROMETRO
ODOMETRO

No crear todavía tipos arbitrarios configurables.

==================================================
2. HISTORIAL APPEND-ONLY
==================================================

Las lecturas deben ser históricas y auditables.

NO permitir UPDATE destructivo de una lectura histórica.

Si una lectura debe corregirse:

- conservar la lectura original;
- registrar la corrección/anulación;
- mantener trazabilidad;
- conservar quién realizó la operación;
- conservar fecha/hora;
- mantener opId/idempotencia.

La historia nunca debe desaparecer silenciosamente.

==================================================
3. VALIDACIÓN DE LECTURAS
==================================================

Implementar la política encontrada durante Discovery:

Si:

lectura actual < lectura anterior

NO eliminar ni alterar la lectura.

Debe conservarse marcada como inconsistente.

La inconsistencia no debe propagarse automáticamente al último valor válido de Activos.

El estado debe ser visible para operación/auditoría.

No inventar reglas adicionales.

==================================================
4. REINICIO DE MEDIDOR
==================================================

Implementar un mecanismo explícito para:

REINICIO_MEDIDOR

Debe requerir una capacidad/permisión específica.

Debe quedar auditado.

Debe registrar:

- motivo;
- usuario;
- fecha;
- valor anterior;
- valor nuevo;
- activo;
- tipo de medidor.

NO asumir que una lectura menor representa automáticamente un reinicio.

==================================================
5. SINCRONIZACIÓN CON ACTIVOS
==================================================

Este punto es CRÍTICO.

Actualmente Activos conserva el último:

- horómetro;
- odómetro.

El nuevo módulo conservará el historial.

Por tanto:

HISTORIAL → module-utilizacion

ÚLTIMO VALOR OPERACIONAL → Activos

No duplicar fuentes de verdad.

Cuando se registre una lectura válida que corresponda al último valor operacional:

- actualizar el último valor en Activos mediante la UoW/outbox existente;
- hacerlo de forma durable;
- serializar por medidor;
- releer la versión cuando corresponda;
- aplicar la regla "gana la lectura más reciente";
- mantener estado de sincronización.

Si la propagación falla:

- NO perder la lectura histórica;
- NO ocultar el error;
- registrar el fallo mediante los mecanismos existentes;
- permitir reintento seguro.

NO modificar el contrato de Activos salvo que sea estrictamente necesario.

Si se determina que es necesario modificar un contrato congelado:

DETENER IMPLEMENTACIÓN
y reportar el GAP a la Dirección.

==================================================
6. TANQUEOS / COMBUSTIBLE
==================================================

Crear la entidad operacional de tanqueo.

Debe estar relacionada con:

- tenantId
- activoId
- fechaHora
- litros
- tipoCombustible
- precioUnitario
- costoTotal
- lectura del medidor en el momento
- operador/usuario
- proveedor/estación cuando pueda reutilizarse Abastecimiento
- observación
- opId
- evidencia si existe soporte contractual

El tanqueo debe poder relacionarse con:

HOROMETRO

o

ODOMETRO

según el tipo de activo.

No asumir que todos los equipos consumen combustible de la misma manera.

Ejemplos:

Maquinaria amarilla:
L/h

Vehículo:
L/100 km

Equipo estático:
puede utilizar otra métrica futura.

==================================================
7. CÁLCULOS
==================================================

En esta fase NO construir un sistema avanzado de indicadores.

Solamente preparar los datos y, cuando sea seguro hacerlo, funciones puras para calcular:

- delta de horómetro;
- delta de odómetro;
- litros por hora;
- litros por 100 km;
- costo por hora;
- costo por km.

REGLA:

Si faltan datos suficientes:

NO devolver 0.

Debe devolverse:

SIN_DATOS

o el equivalente contractual existente.

Ejemplo:

Sin horómetro válido:
consumo L/h = SIN DATOS

No:

consumo L/h = 0

9. COSTOS
