# DIRECTIVA OFICIAL — DELTAOPS LITE-11
# «Auditoría final, hardening, preparación para producción y base del manual»

## 0. OBJETIVO DE LA FASE

Esta es la FASE FINAL TÉCNICA de DeltaOps Lite.

NO crear DeltaOps Lite-12, Lite-13 ni nuevas fases automáticamente.

NO ampliar el alcance funcional.

NO convertir DeltaOps Lite nuevamente en un ERP/CMMS empresarial sobredimensionado.

El objetivo es determinar si DeltaOps Lite está realmente preparada para pasar a producción.

La filosofía de esta fase es:

AUDITAR → CORREGIR → PROBAR → ASEGURAR → DOCUMENTAR → DETENERSE

El producto ya tiene:

- activos;
- centros de costos;
- horómetro;
- rutinas;
- preoperacional;
- checklist;
- hallazgos;
- OT;
- ejecución;
- validación;
- cierre;
- mano de obra;
- repuestos/insumos;
- combustible;
- hoja de vida;
- indicadores;
- datos históricos reales;
- importador histórico;
- RBAC;
- RLS;
- aislamiento multi-tenant;
- UX/UI;
- responsive;
- tema claro/oscuro.

Por lo tanto, el objetivo NO es agregar más funcionalidades.

El objetivo es demostrar que lo existente es:

SEGUR0 + ESTABLE + CONSISTENTE + RECUPERABLE + USABLE + DESPLEGABLE.

# 2. REGLA CRÍTICA SOBRE LA BASE DE DATOS

Durante LITE-10 ocurrió un incidente:

Las suites de integración PostgreSQL ejecutadas contra la BD compartida eliminaron el tenant demo y los datos históricos reales importados durante LITE-09.

Los datos fueron restaurados mediante:

- seed;
- importador oficial;
- importación idempotente;
- verificación SQL.

Este incidente NO debe volver a ser posible.

## REQUISITO BLOQUEANTE

NINGUNA SUITE DE TEST AUTOMATIZADA DEBE PODER DESTRUIR, TRUNCAR, REEMPLAZAR O MODIFICAR DATOS HISTÓRICOS REALES DE UNA BD DE DESARROLLO/DEMOSTRACIÓN.

La separación debe ser conceptualmente:

TEST:

tests
↓
BASE DE DATOS DE TEST AISLADA

DESARROLLO:

aplicación
↓
BASE DE DATOS DE DESARROLLO
↓
datos demo/históricos

PRODUCCIÓN:

aplicación
↓
BASE DE DATOS PRODUCCIÓN
↓
datos reales

No permitir que una suite de test destructiva apunte accidentalmente a DATABASE_URL de desarrollo.

# 3. HARDENING DE TESTS

Auditar todas las suites que utilicen PostgreSQL.

Buscar especialmente:

- TRUNCATE;
- DELETE masivo;
- DROP;
- RESET;
- seed destructivo;
- migraciones destructivas;
- limpieza global;
- DATABASE_URL;
- variables de conexión;
- scripts de integración;
- fixtures;
- beforeAll/beforeEach;
- afterAll/afterEach.

Determinar exactamente qué suites pueden modificar datos.

## Implementar protección fail-fast

Una suite de test destructiva debe ABORTAR si detecta que está conectada a una base de datos que no es inequívocamente una BD de test.

No utilizar heurísticas débiles como solamente:

NODE_ENV=test

porque puede ser insuficiente.

Implementar la protección más segura compatible con la arquitectura actual.

Ejemplos aceptables si encajan con el proyecto:

- DATABASE_TEST_URL obligatoria para suites destructivas;
- marcador explícito de BD de test;
- nombre de base de datos permitido;
- usuario de test dedicado;
- combinación de protecciones.

NO asumir que cambiar una variable es suficiente.

Documentar:

- cómo ejecutar tests;
- qué BD utilizan;
- cuáles son destructivos;
- cómo se evita apuntar a desarrollo/producción.

# 4. PRODUCCIÓN NUNCA DEBE SER DESTINO DE TEST
