## 11. Estrategia de retiro (secuencia ajustada)

Ajuste sobre la secuencia sugerida: por la **regeneración del cliente compartido**, las fases frontend + API + contrato deben acoplarse; y el **health gate** debe migrarse ANTES/junto con la eliminación del router health.

- **FASE A — Eliminar consumo.** Retirar `artifacts/sgma` del árbol y de la instalación (dir + su `artifact.toml`). DeltaOps intacto. *Verificación: build de DeltaOps OK; workflow sgma deja de existir.*
- **FASE B — Migrar health gate (pre-requisito de C).** Editar `artifacts/api-server/.replit-artifact/artifact.toml` `health.startup.path` → `/api/deltaops/platform/health` (o añadir `/healthz` trivial en router DeltaOps). *Verificación: deploy health probe apunta a endpoint vigente.*
- **FASE C — Eliminar API legacy + contratos + regenerar (cambio ATÓMICO).** Quitar los 10 routers + `routes/index.ts` + `app.ts:4,101`; eliminar paths/schemas SGMA de `openapi.yaml` (conservando `Error` y todo `Deltaops*`); ejecutar `pnpm --filter @workspace/api-spec run codegen` para regenerar `api-client-react`/`api-zod` sin símbolos legacy. *Debe ir junto para que typecheck/build no rompan.* *Verificación: typecheck + build del monorepo OK; api-client-react sin hooks legacy; DeltaOps compila usando `useDeltaops*`.*
- **FASE D — Eliminar seeds/scripts + schemas drizzle.** Quitar `seed-sgma.ts` + entrada `scripts/package.json`; eliminar `lib/db/src/schema/{9}.ts` y ajustar el barrel `lib/db/src/index.ts`. *Verificación: typecheck OK; sin exports colgados.*
- **FASE E — Limpiar config/docs/deps.** Actualizar `replit.md`, `MODULOS_EXISTENTES.md`, `ARQUITECTURA_ACTUAL.md`, `REUTILIZACION.md`, `lib/module-activos/docs/api.md`. *Verificación: docs coherentes.*
- **FASE F — Backup + DROP de tablas `public.*` por migración.** Nueva migración `deltaops`/DDL que hace `DROP TABLE public.<9>` (seguro: sin FK/vista/trigger/función), previo `pg_dump` (§13). *Verificación: esquema `public` vacío; DeltaOps opera sobre `deltaops.*` sin cambios.*
- **FASE G — Validación completa DeltaOps** (§10/§13 criterios).

Cada fase = commit normal reversible.

## 12. Estrategia de rollback

- **Código:** cada fase es un commit atómico; `git revert <commit>` restaura routers/frontend/contratos/schemas. El historial NO se altera. Recomendado: tag `pre-retiro-sgma` antes de FASE A.
- **Regeneración del cliente:** reversible regenerando desde el `openapi.yaml` restaurado (`git revert` + `codegen`).
- **Base de datos (crítico, irreversible sin backup):** ANTES de la FASE F, ejecutar `pg_dump` de las 9 tablas:
  `pg_dump "$DATABASE_URL" --schema=public --format=custom --file=backup-sgma-public-YYYYMMDD.dump` (o `--table=public.work_orders …` para las 9). Guardar el artefacto fuera del repo. Restauración: `pg_restore` de las tablas. Dado que son datos demo, el backup es por prudencia, no por valor operativo.
- **Deploy:** si el health probe falla tras FASE C sin FASE B, revertir `artifact.toml`; por eso B precede a C.
