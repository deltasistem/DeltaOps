### HALLAZGO I-03 (ALTO) — Fallback peligroso a `DATABASE_URL` (superusuario)

`lib/db/src/index.ts::resolveRuntimeConnectionString()` (`:36-61`): si **falta** `DELTAOPS_APP_PASSWORD` (o `PGHOST`/`PGDATABASE`), el pool **retorna `process.env.DATABASE_URL`** — que es la conexión **admin `postgres` (superusuario + BYPASSRLS)** gestionada por el proveedor.

- **Cuándo se activa:** cualquier arranque de runtime sin el secreto `DELTAOPS_APP_PASSWORD` presente/legible (secreto no propagado, entorno mal configurado, despliegue externo que olvide setearlo, rollback deliberado).
- **Riesgo en producción:** el runtime reconectaría como superusuario ⇒ **BYPASSRLS ⇒ H-02 reintroducida** (aislamiento multi-tenant inefectivo) de forma **silenciosa** (no hay log de advertencia, no distingue `NODE_ENV`). El diseño lo etiqueta como “rollback de runtime”, pero como *default silencioso en producción* es un riesgo.
- **Recomendación (NO implementar aquí):** en `NODE_ENV=production`, **fail-fast** si falta la credencial de rol de mínimo privilegio en lugar de degradar a `postgres`; o emitir advertencia crítica + métrica. Decisión de Dirección.

> Se documenta el hallazgo. **No se corrige** (regla absoluta).

## 6. DOMINIOS Y HTTPS

**Topología actual (Replit):** un único origen tras el proxy de la plataforma; el frontend (`/deltaops/`) y la API (`/api`) comparten host ⇒ same-origin; TLS lo termina el proxy de Replit; `trust proxy = 1` permite cookies `secure`. Health startup gate configurado.

**Requisitos para producción (identificados, sin asumir proveedor):**

- **Dominio/subdominio:** definir dominio productivo. Si API y frontend comparten origen (recomendado, como hoy), cookies host-only + `sameSite=lax` bastan. Si se separan (p. ej. `api.` vs `app.`), habrá que ajustar CORS (§7), `sameSite=none; Secure` y posiblemente `COOKIE_DOMAIN`.
- **HTTPS/TLS:** obligatorio en prod (cookie `secure`); hoy lo aporta el proxy de Replit. En host externo hará falta reverse proxy con TLS (nginx/Caddy/Traefik) o balanceador gestionado + redirección HTTP→HTTPS.
- **Reverse proxy:** debe reenviar `X-Forwarded-Proto` (ya contemplado por `trust proxy = 1`).
- **WebSocket/SSE:** no se detectaron; no hay requisitos de upgrade.
- **Health checks:** `/api/deltaops/platform/health` (liveness) y `/api/deltaops/platform/ready` (readiness con DB+SESSION_SECRET). Ver I-09.

No hay dependencia de dominio hardcodeada en código (frontend usa rutas relativas).

## 7. CORS

- **Implementación actual:** `app.use(cors())` (`app.ts:63`), **sin opciones** ⇒ `Access-Control-Allow-Origin: *` (wildcard), métodos/headers por defecto del paquete, **sin `credentials:true`**.
- **Comportamiento dev = prod:** idéntico (no distingue entorno).
- **Riesgo real hoy:** MITIGADO por la topología same-origin (el navegador no hace CORS con cookies cross-origin, y `credentials` no está activado). Aun así, expone la API a lecturas cross-origin sin credenciales desde cualquier origen.

### HALLAZGO I-05 (ALTO) — CORS wildcard

**Qué debería cambiar para producción (NO implementar):**
- Restringir `origin` a una allowlist explícita (dominio(s) del frontend productivo), configurable por env (p. ej. `CORS_ORIGIN`).
- Si en el futuro el frontend se sirve en un origen distinto de la API y necesita cookies, activar `credentials:true` **con** `origin` específico (nunca wildcard + credentials, que el navegador rechaza).
- Limitar métodos/headers a los usados.

> Documentado. **No se modifica CORS** (regla absoluta).

## 8. STORAGE Y ARCHIVOS

**La plataforma es REFERENCIA-ONLY: no almacena binarios.** Evidencia:

- `attachment-serve.ts`: emite/verifica **URLs firmadas HMAC-SHA256** (payload `tenant:id:expires`, `timingSafeEqual`), con TTL; la firma ES la autorización (sin sesión). Devuelve **metadatos** del adjunto (tenant-scoped), nunca binario. Clave HMAC = `SESSION_SECRET` (I-02).
- `lib/platform/src/services/attachment.ts`: idéntico esquema de firma (`platform.attachment.signedUrl`).
- **No hay** `multer`/uploads, ni escritura de binarios al filesystem, ni `fs.writeFile` de contenido de usuario. El seed registra solo *referencias* (`platform.attachment.register`).

**Persistencia:** los metadatos de adjuntos viven en PostgreSQL (persistente, respaldable). No hay estado en filesystem local que dependa de sobrevivir reinicios (coherente con `deploymentTarget = autoscale`, efímero). La única dependencia de disco es `dist/` (build) — recreable.

**Riesgo de producción:** bajo, salvo I-02 (reutilización de `SESSION_SECRET` como clave de firma: rotarlo invalidaría todas las URLs firmadas vigentes). Si en el futuro se almacenan binarios, se requerirá almacenamiento externo (S3/GCS) — hoy no aplica.
