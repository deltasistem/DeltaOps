## 1. Estado actual

**Veredicto: la RLS NO es efectiva en runtime.** Confirmado H-02 de DGP-023.

Evidencia — identidad de la conexión de la aplicación:

```
psql "$DATABASE_URL" -c "SELECT current_user, session_user, current_database(), current_schema();"
→ current_user=postgres | session_user=postgres | current_database=heliumdb | current_schema=public
```

Evidencia — atributos del rol conectado:

```
psql: SELECT rolname, rolsuper, rolbypassrls, rolcreatedb, rolcreaterole, rolreplication, rolinherit, rolcanlogin
      FROM pg_roles WHERE rolname = current_user;
→ postgres | rolsuper=t | rolbypassrls=t | rolcreatedb=t | rolcreaterole=t | rolreplication=t | rolinherit=t | rolcanlogin=t
```

El rol de runtime `postgres` es **SUPERUSER** y tiene **BYPASSRLS = true**. En PostgreSQL, un rol con `BYPASSRLS` (y todo superusuario) **ignora todas las políticas RLS**. Por tanto:

- Las 167 políticas declaradas en `deltaops.*` están **inactivas en runtime**.
- El aislamiento por tenant descansa **enteramente en la capa de aplicación** (el `WHERE tenant_id = …` implícito de las políticas se compila a un no-op, y el filtrado real proviene del `set_config('app.tenant_id', …)` + predicados de la app; ver §5).
- Además, la conexión se realiza sobre la base `heliumdb` (Neon/Replit), cuyo `datdba` es `postgres`.

**Conclusión:** RLS efectiva = **NO**. Motivo primario: rol de runtime superusuario con BYPASSRLS. Motivo secundario (aplicaría aun sin superusuario): ninguna tabla tiene `FORCE ROW LEVEL SECURITY` y todas son propiedad del rol de runtime, por lo que el owner también evadiría RLS (ver §2, §4, §12).

## 2. Inventario RLS

Evidencia — recuento global del esquema `deltaops`:

```
psql: total_tables=174 | with_rls(relrowsecurity)=167 | with_force(relforcerowsecurity)=0 | no_rls=7
psql: pg_tables por esquema → deltaops=174 ; public=0 (SGMA retirado en DGP-023.2, confirmado)
```

Evidencia — forma de las políticas (uniforme):

```
psql: SELECT cmd, roles, qual, with_check, count(*) FROM pg_policies WHERE schemaname='deltaops' GROUP BY 1,2,3,4;
→ cmd=ALL | roles={public} | qual=(tenant_id = current_setting('app.tenant_id'::text, true))
        | with_check=(tenant_id = current_setting('app.tenant_id'::text, true)) | count=167
psql: tablas con RLS habilitada pero SIN políticas → 0
psql: políticas que NO coinciden con el predicado estándar → 0
```

**Matriz-resumen de RLS (`deltaops.*`, 174 tablas):**

| Categoría | Cantidad | Descripción | Clasificación de riesgo (con rol superusuario actual) |
|---|---|---|---|
| RLS = ON, FORCE = OFF, 1 policy tenant | **167** | Predicado uniforme `tenant_id = current_setting('app.tenant_id', true)`, `cmd=ALL`, rol `public`, USING + WITH CHECK | **ALTO** — la RLS es un "cinturón inactivo": bypassada por superusuario Y por owner (sin FORCE). Defensa en profundidad ausente. |
| RLS = ON, FORCE = ON | **0** | Ninguna | — (gap: ver §12) |
| RLS = OFF con columna `tenant_id` | **1** (`idn_memberships`) | Tabla tenant-scoped sin RLS | **CRÍTICO/ALTO** — contiene el vínculo identidad↔tenant↔rol; sin protección de fila (ver §4) |
| RLS = OFF sin columna tenant | **6** | `idn_identities`, `users`, `sessions`, `kernel_outbox`, `kernel_dead_letter`, `ntf_email_templates` | Variable (ver §4) |

Notas sobre el predicado uniforme:

- USING y WITH CHECK son **idénticos** en las 167 tablas: bloquea SELECT/UPDATE/DELETE de filas de otro tenant y **también** INSERT/UPDATE hacia un `tenant_id` distinto del contexto (`WITH CHECK`). Diseño correcto para aislamiento bidireccional — **cuando la RLS esté activa**.
- `current_setting('app.tenant_id', true)` usa el segundo argumento `true` (missing_ok): si el GUC no está fijado, retorna `NULL`. Con RLS activa, `tenant_id = NULL` es `UNKNOWN` ⇒ ninguna fila pasa ⇒ **fail-closed** (una transacción sin contexto no ve ni escribe nada). Esto es deseable y debe preservarse.
- Rol `{public}`: la política aplica a todos los roles no-bypass. Un futuro `deltaops_app` (no superusuario, no owner, no bypass) quedaría sujeto a ella sin cambios en las policies.

Confirmación cruzada: 168 tablas tienen columna `tenant_id` (`information_schema.columns`); 167 tienen RLS+policy ⇒ **exactamente 1 tabla tenant-scoped sin RLS** = `idn_memberships`.

## 4. Owners

Evidencia:

```
psql: SELECT pg_get_userbyid(relowner), count(*) FROM pg_class ... WHERE nspname='deltaops' AND relkind='r' GROUP BY 1;
→ postgres | 174
psql: SELECT nspname, pg_get_userbyid(nspowner) FROM pg_namespace → deltaops=postgres ; public=pg_database_owner
psql: SELECT datname, pg_get_userbyid(datdba) FROM pg_database WHERE datname=current_database() → heliumdb | postgres
```

**Las 174 tablas de `deltaops.*`, el esquema `deltaops` y la base `heliumdb` son propiedad de `postgres`** (el mismo rol de runtime).

Implicación crítica para RLS: en PostgreSQL, el **owner de una tabla evade sus políticas RLS salvo que se declare `FORCE ROW LEVEL SECURITY`**. Por tanto, aunque se corrigiera el runtime a un rol no-superusuario y sin BYPASSRLS, **si ese rol siguiera siendo owner de las tablas, seguiría evadiendo la RLS**. La solución requiere separar owner (migración) de runtime (aplicación) — ver §10/§11 — y/o aplicar FORCE (§12).

Evidencia — tablas sin RLS y su owner:

```
psql: idn_identities|postgres, idn_memberships|postgres, kernel_dead_letter|postgres,
      kernel_outbox|postgres, ntf_email_templates|postgres, sessions|postgres, users|postgres
```

## 5. Tenant context (modelo de tenant · directiva §6)

**¿Dónde nace `tenant_id`?** Server-side, de la fila espejo de la sesión. En cada router de módulo el guard lee `req.session.deltaopsUserId`, carga la fila de `deltaops.users` (id, rol, tenant) y compone el `ExecutionContext` con el tenant derivado del servidor:

- `artifacts/api-server/src/routes/deltaops/activos-module.ts:20` (`req.session?.deltaopsUserId`), `:33` (`contextForActivos(String(user.id), user.rol, user.tenant)`).
- El middleware `requireIdentityForModules` re-fija el `deltaopsUserId` a la fila espejo (identidad, tenant) de la sesión (referenciado en DGP-023 §8.1).

**¿Puede venir del frontend / body / ser modificado por el usuario?** No. `rg "body.(tenant|tenantId)"` en producción → 0 coincidencias (documentado en DGP-023 §8.2). El tenant siempre proviene del servidor.

**¿Cómo se fija en la transacción?** Vía `SELECT set_config('app.tenant_id', $1, true)` — el tercer argumento `true` lo hace **transaction-local** (equivalente a `SET LOCAL`). Se establece dentro de cada UoW/transacción, tanto en escrituras como en lecturas. Evidencia (patrón replicado en 15 repositorios + helpers):

```
lib/module-activos/src/infrastructure/repository.ts:393   (escritura vía pgSessionOf(uow))
lib/module-activos/src/infrastructure/repository.ts:404   (lectura vía withTenantRead: BEGIN → set_config → fn → COMMIT)
lib/module-ordenes|inventario|planes|preventivo|correctivo|abastecimiento|reference|manodeobra|
    costos|analytics|utilizacion/src/infrastructure/repository.ts  (mismo patrón)
lib/platform/src/core/record-store.ts:191                 (fijarTenant vía set_config)
artifacts/api-server/src/deltaops/identity/db-helpers.ts:25  (withTenant: BEGIN → set_config → fn → COMMIT)
artifacts/api-server/src/routes/deltaops/reference-module.ts:183,199 (recibos de sync)
artifacts/api-server/src/routes/deltaops/costos-orquestador.ts:126
```

**¿Se conserva durante toda la transacción?** Sí, por ser `set_config(..., true)` (local a la transacción). **¿Se pierde en conexiones pooled?** No: al ser transaction-local, al liberar el cliente (`client.release()`) el GUC se descarta con el COMMIT/ROLLBACK; no persiste para la siguiente petición (ver §6).

**Ruta de acceso SIN tenant (relevante para el futuro rol):** `withGlobal` (`db-helpers.ts:42-51`) abre una conexión **sin** `set_config` para leer identidad global (`idn_identities`/`idn_memberships`). Esto funciona hoy porque estas tablas no tienen RLS; con un rol no-superusuario y RLS/FORCE sobre `idn_memberships`, esta ruta requeriría contexto o una policy específica (ver §10, §12 — riesgo de fail-closed en login).

**El "cinturón y tirante":** hoy el "tirante" (efectivo) es el `set_config` + los predicados de la app; el "cinturón" (RLS) está inactivo por H-02. Un bug que omita `set_config`/`WHERE` **no quedaría contenido** por RLS en el estado actual.

## 6. Pooling

Evidencia:

- Pool único en `lib/db/src/index.ts:13` (`new Pool({ connectionString: process.env.DATABASE_URL })`), reutilizado por API, identity y seed.
- Todo acceso fija el tenant **transaction-local** dentro de un `BEGIN…COMMIT`:
  - Escrituras: `PgUnitOfWork.execute` (`lib/kernel/src/adapters/pg.ts:70-90`) hace `connect → BEGIN → work → COMMIT/ROLLBACK → release`. El `set_config` lo emite el repositorio dentro de ese `work` (`repository.ts:393`).
  - Lecturas: `withTenantRead` (`lib/module-activos/src/infrastructure/repository.ts:396-414`) y `withTenant` (`db-helpers.ts:18-39`) hacen `connect → BEGIN → set_config(local) → fn → COMMIT → release`.

**Riesgo de contaminación entre solicitudes: BAJO en el estado actual.** Como el GUC es transaction-local (`true`), no sobrevive al `release()`; la petición B no hereda el `app.tenant_id` de la petición A. El riesgo residual sería:

1. Una consulta ejecutada **fuera** de un `BEGIN…COMMIT` con `set_config` (p. ej. `pool.query(...)` directo). Los `pool.query` directos detectados son del **outbox** (`pg.ts:148,170,184,233`), que opera sobre `kernel_outbox` (sin columna tenant) ⇒ no depende de `app.tenant_id`. No se detectó lectura de tablas tenant-scoped vía `pool.query` sin transacción.
2. Un `SET` a nivel de sesión (no `LOCAL`) — **no** se usa; todos los usos son `set_config(..., true)`.

**Requisito para la fase de implementación:** al pasar a `deltaops_app` con RLS efectiva, la garantía "Request A → tenant A / Request B → tenant B" debe mantenerse con la misma disciplina transaction-local, y debe añadirse una salvaguarda fail-closed (RLS ya niega todo si el GUC no está fijado, gracias a `current_setting(..., true)` → NULL).

## 7. Workers

**No existe un worker de fondo con conexión persistente propia.** El procesamiento de outbox se dispara **in-process** tras los comandos de cada módulo (drenaje sincrónico), no como daemon separado. Evidencia:

- `OutboxProcessor.processPending` (`lib/kernel/src/events/outbox.ts:59-95`): `claimPending → dispatch → markProcessed/releaseForRetry/markDead`. Entrega **at-least-once**; los handlers DEBEN ser idempotentes (comentario `outbox.ts:57`).
- Reclamo atómico con lease: `claimPending` usa `UPDATE … FOR UPDATE SKIP LOCKED` + `claimed_until = now()+60s` (`pg.ts:146-166`), seguro con procesadores concurrentes; un procesador caído libera por expiración del lease.
- El drenaje se invoca desde los routers de módulo tras cada efecto (múltiples referencias `…kernel.<procesador>()` en `*-module.ts` / `*-runtime.ts`).

**Contexto tenant del worker:** el `OutboxProcessor` **no** fija `app.tenant_id`; opera sobre `kernel_outbox` (tabla sin columna tenant, vía `pool.query` directo). El tenant se recupera del **payload del evento**: evidencia — la práctica totalidad de los eventos del outbox lleva `tenantId` en el payload, con **una excepción real**:

```
psql: SELECT (payload ? 'tenantId') AS has_tenant, count(*) FROM deltaops.kernel_outbox GROUP BY 1;
→ t | 21.620   ·   f | 163
```

Las 163 filas sin `tenantId` son todas del tipo `modulo.manodeobra.valoracion-registrada` (ya procesadas). Hoy no rompe nada porque ese evento no tiene handler de outbox que materialice datos tenant-scoped (Costos lee las valoraciones sincrónicamente vía query pública, no vía outbox), pero demuestra que la garantía "todo evento lleva tenantId" **no es un invariante del kernel**: con RLS activa, un futuro handler sobre un evento sin tenant fallaría-cerrado. Este tipo de evento debe incorporarse a la batería de pruebas de §15 antes de FORCE.

El handler que materializa efectos (read models, sincronizaciones) toma `payload.tenantId` y abre su propia UoW/lectura con `set_config` de ese tenant. **Riesgo:** si algún handler omitiera derivar el tenant del payload, con RLS activa fallaría-cerrado (no vería/escribiría nada) — comportamiento seguro pero que rompería la funcionalidad; debe cubrirse en pruebas (§15). Debe documentarse el contexto exacto de cada handler antes de FORCE.

## 8. Servicios

**Principal de servicio `system:utilizacion-sync`** (directiva §13). Evidencia:

- `artifacts/api-server/src/routes/deltaops/utilizacion-runtime.ts:106` (`export const ACTOR_SERVICIO_SYNC = "system:utilizacion-sync"`), `:109` (`PERMISOS_SERVICIO_SYNC = ["modulo.activos.operar"]`), `:111-130` (`contextForActivosServicioSync(tenantId, originadorActorId)`).

Determinaciones:

- **Cómo se autentica:** NO es un usuario ni un rol de PostgreSQL. Es un **actor de aplicación** (principal del kernel) con `rol: "system"` y permisos de mínimo privilegio (`modulo.activos.operar`). No fabrica el rol `admin`.
- **Qué conexión DB usa:** la misma pool única / mismo rol `postgres`. No tiene conexión propia.
- **Qué permisos DB necesita:** los mismos que cualquier operación tenant-scoped de Activos. Ejecuta con `metadata.tenantId` (`utilizacion-runtime.ts:123-124`) a través de la UoW/repositorio de Activos, que fija `set_config('app.tenant_id', …)`.
- **¿Necesita BYPASSRLS?** **No.** Opera dentro de un tenant concreto (el tenant de la lectura de utilización que origina la propagación). Puede funcionar íntegramente mediante contexto tenant.
- **¿Requiere SECURITY DEFINER?** **No** para este principal. No cruza tenants ni accede a tablas globales privilegiadas.

Otros actores de servicio detectados:

- `manodeobra-runtime.ts` — `principal: { id: "nmanodeobra", rol: "servicio", permisos: [P_VALORAR, P_READ] }`: actor de aplicación tenant-scoped; **no** requiere privilegio DB elevado.

**Operaciones internas (directiva §12) — tabla de evaluación:**

| Proceso | ¿Tenant-scoped? | ¿Necesita privilegio DB elevado? | Alternativa segura |
|---|---|---|---|
| Utilización → Activos (sync) | Sí | No | Contexto tenant + `set_config` (ya implementado) |
| Inventario → Costos | Sí | No | Handler deriva `payload.tenantId` |
| Sesiones → Mano de obra / valoración | Sí | No | Contexto tenant + principal de servicio app-layer |
| Órdenes (workflow/estado) | Sí | No | Contexto tenant |

| Seed demo | Multi-tenant (crea datos) | Discutible: hoy corre como owner | Ejecutar seed con **migration/owner role**, no con runtime role |
| Analytics (indicadores/read models) | Sí | No | Contexto tenant |
| Administración / SUPER_ADMIN | Cross-tenant (lectura global) | **Sí, potencialmente** | Función `SECURITY DEFINER` acotada o rol admin separado (documentar; NO crear en Discovery) |

Ningún proceso de negocio identificado requiere `BYPASSRLS`. Los únicos casos que necesitan acceso "cross-tenant" son administración (SUPER_ADMIN) e identidad global, resolubles con GRANT acotado y/o `SECURITY DEFINER` bien delimitado — **no** con un rol runtime que bypassa RLS globalmente.

| R-9 | Seed/migraciones corriendo como runtime | L | El runtime hoy ES owner; sin separación migración/runtime | **MEDIO** |

**Hallazgos que obligan a DETENERSE antes de implementar (§13/§20):**

- **STOP-1 (R-2/R-5):** cambiar el runtime a un rol no-superusuario **no basta** si ese rol es owner o si `idn_memberships`/identidad quedan sin una estrategia de acceso. Debe resolverse primero la separación owner/runtime y la ruta de login (`withGlobal`). Implementar sin esto **romperá el login** o dejará RLS inefectiva.
- **STOP-2 (infra):** la BD es `heliumdb` gestionada por Replit/Neon. Crear roles, cambiar owner o `DATABASE_URL` puede depender de capacidades del proveedor no verificadas en Discovery (¿permite el plan crear roles LOGIN y transferir ownership?). Requiere validación de Dirección/infra antes de la Fase A.

## 10. Diseño de application role (propuesto — NO implementar)

Rol de aplicación propuesto: **`deltaops_app`** (LOGIN).

Atributos exigidos:

- `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`.
- `LOGIN` con contraseña gestionada por secreto del entorno (NUNCA en repo/docs).
- `INHERIT` (para heredar de un rol de privilegios `deltaops_app_rw` si se opta por separar login de privilegios).

Privilegios (mínimo necesario, a conceder en Fase C — NO ahora):

- `GRANT USAGE ON SCHEMA deltaops` (no `CREATE`).
- `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA deltaops` (sin `TRUNCATE`, sin `REFERENCES`, sin DDL). Sujeto a RLS.
- `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA deltaops`.
- **Sin** `ALTER`/`DROP`/`CREATE` sobre estructura (no es owner).
- Acceso explícito a tablas de kernel (`kernel_outbox`, `kernel_dead_letter`) para el drenaje.

**Recomendación LOGIN vs NOLOGIN:** usar un **rol de privilegios `NOLOGIN`** (`deltaops_app_rw`) que agrupe los GRANT, y un **rol `LOGIN` (`deltaops_app`)** miembro de él. Ventajas: rotar la credencial de login sin re-otorgar privilegios; poder crear futuros roles login (p. ej. réplica de lectura) reutilizando el mismo conjunto de privilegios. Es la alternativa más segura y mantenible.

**Interacción con RLS:** como las policies aplican al rol `public` (§2), `deltaops_app` queda sujeto automáticamente. Debe resolverse la ruta de identidad global:

- Opción A (recomendada): `idn_identities`/`idn_memberships` **sin RLS** pero con **GRANT acotado** a `deltaops_app` (SELECT/INSERT/UPDATE), manteniendo el aislamiento por filtro app-layer y auditando ese acceso. Documentar como "global by design".
- Opción B: RLS con policy específica en `idn_memberships` que permita, además del predicado tenant, el acceso por `identity_id` durante login (requiere un GUC `app.identity_id`). Más complejo; evaluar en implementación.

## 11. Diseño de migration/owner role (propuesto — NO implementar)

Rol de migración/owner: **`deltaops_owner`** (o reutilizar un rol administrativo del proveedor si `postgres` no puede transferirse).

- Es el **owner** del esquema `deltaops` y de sus tablas/secuencias/funciones.
- Ejecuta migraciones (`lib/db/migrations/deltaops/*.sql`), `drizzle-kit push`, creación de tablas/índices/policies/triggers y el **seed**.
- Atributos: `NOSUPERUSER` si el proveedor lo permite; puede requerir `CREATEROLE` solo si gestiona GRANT (evaluar). **No** debe usarse como runtime.
- Puede tener `BYPASSRLS`? **Preferiblemente NO**; con FORCE activo, incluso el owner queda sujeto a RLS, por lo que el seed multi-tenant deberá fijar `app.tenant_id` por tenant (o ejecutarse antes de FORCE). Documentar.

**Separación de responsabilidades (viable y recomendada):**

```
deltaops_owner  (owner + DDL + migraciones + seed)   ── NOLOGIN o LOGIN restringido a CI/operador
        │  es dueño de las tablas
        ▼
deltaops_app_rw (NOLOGIN, GRANT SELECT/INSERT/UPDATE/DELETE)  ── privilegios
        │  miembro
        ▼
deltaops_app    (LOGIN, runtime)  ── sujeto a RLS (no owner, no bypass)
        │
        ▼
   RLS efectiva (policies tenant_id) + FORCE
```

Esta cadena garantiza que el rol de runtime **no pueda evadir RLS por ser propietario** (no lo es) ni por atributo (no bypass). El owner sigue pudiendo hacer DDL sin exponer la evasión al runtime.

## 12. FORCE RLS (propuesto — NO aplicar)

**Estado:** 0 tablas con `relforcerowsecurity` (§2). Ninguna migración contiene `FORCE ROW LEVEL SECURITY` (`rg` → NONE FOUND).

**Por qué es necesario:** con la separación owner/runtime de §11, el runtime dejaría de ser owner y quedaría sujeto a RLS sin FORCE. Sin embargo, `FORCE` sigue siendo **recomendable** como defensa en profundidad para el caso en que el owner ejecute lógica de datos (seed, backfills, funciones), de modo que ni siquiera el owner evada el aislamiento salvo por vías controladas.

**Tablas candidatas a FORCE:** las **167** tablas tenant-scoped con RLS ya habilitada + `idn_memberships` y `users` una vez se les añada RLS.

| Grupo | Motivo | Riesgo al aplicar FORCE | Impacto esperado |
|---|---|---|---|
| 167 tablas de negocio | Impedir evasión por owner; RLS realmente efectiva | Seed/migraciones/backfills del owner deberán fijar `app.tenant_id` por tenant o desactivar FORCE temporalmente para operaciones globales | Ninguno en runtime (ya fijan tenant); sí en seed/mantenimiento |
| `idn_memberships`, `users` | Tenant-scoped; hoy sin RLS (R-3/R-4) | La ruta de **login** (`withGlobal`, sin tenant) fallaría-cerrado ⇒ **rompería autenticación** si no se ajusta primero | **ALTO** — requiere estrategia de identidad (§10 Opción A/B) antes de FORCE |
| `idn_identities` | Global por diseño; sin `tenant_id` | RLS por tenant no aplicable | No aplicar FORCE por tenant; proteger por GRANT |
| `kernel_outbox`/`dead_letter` | Sin columna tenant | RLS clásica no aplicable | Proteger por GRANT; no FORCE |

**Regla de oro:** FORCE debe aplicarse **después** de migrar el runtime a `deltaops_app` y **después** de validar tenant A/B, nunca antes (evitaría diagnosticar). Especial atención a propietarios, migraciones, seeds y handlers de outbox.

## 14. Rollback (propuesto)

Principio: **el fallback NO es "volver a superuser permanentemente".**

Estrategia por capas:

1. **Rollback del runtime (Fase G):** el cambio de runtime es un cambio de **secreto** (`DATABASE_URL` → `deltaops_app`). Rollback = revertir el secreto a la conexión anterior y reiniciar. Como medida **temporal y auditada** (ventana corta), puede volverse a la conexión previa mientras se diagnostica; NO como estado final. Registrar la reversión y su causa.
2. **RLS/FORCE que bloquea operación legítima (Fase E):** `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` sobre la tabla específica (reversible, granular) mientras se corrige la policy o el contexto; luego re-aplicar FORCE. No desactivar RLS globalmente.
3. **Worker/outbox pierde permisos:** conceder el GRANT faltante sobre la tabla de kernel (aditivo); no elevar a superusuario.
4. **Pérdida de contexto tenant / login roto:** revertir la RLS/FORCE de las tablas de identidad a la estrategia previa (Opción A sin RLS) y re-planificar; el login debe restaurarse sin recurrir a bypass global.
5. **Fallo de migración (Fases A–D):** las migraciones son `.sql` versionadas; preparar scripts de reversión por fase (DROP POLICY / REVOKE / DROP ROLE si aplica). Probar en staging.
6. **Problemas de pooling:** ajustar tamaño de pool / disciplina transaccional; no relajar el aislamiento.

Todo rollback debe ser **granular, reversible y auditado**, y dejar el sistema en un estado sin superusuario en runtime tan pronto como sea posible.

## 15. Pruebas (test de contención A/B — diseño, NO ejecutar mutaciones ahora)

Objetivo: demostrar que, conectado como `deltaops_app` (no superusuario, no bypass) y con RLS+FORCE, Tenant A **no puede** `SELECT`/`INSERT`/`UPDATE`/`DELETE` sobre datos de Tenant B, **incluso si el código omite el filtro**.

Fixtures propuestos (para la fase de implementación, en staging):

- Tenant A y Tenant B con datos en tablas representativas (`act_activos`, `ord_ordenes`, `inv_*`, `idn_memberships`).
- Conexión bajo `deltaops_app`.

Casos (ejecutar como `deltaops_app`):

1. `set_config('app.tenant_id', 'A')` → `SELECT * FROM deltaops.act_activos` **sin** `WHERE` ⇒ debe devolver **solo** filas de A (RLS filtra).
2. `set_config('app.tenant_id', 'A')` → `SELECT … WHERE tenant_id='B'` ⇒ **0 filas**.
3. `set_config('app.tenant_id', 'A')` → `INSERT … (tenant_id) VALUES ('B', …)` ⇒ **error/rechazo** por WITH CHECK.
4. `set_config('app.tenant_id', 'A')` → `UPDATE … SET tenant_id='B'` ⇒ **rechazo** por WITH CHECK.
5. `set_config('app.tenant_id', 'A')` → `DELETE FROM … WHERE tenant_id='B'` ⇒ **0 filas afectadas**.
6. **Sin** `set_config` (contexto ausente) ⇒ **0 filas** en SELECT y rechazo en escritura (fail-closed).
7. `idn_memberships`/`users` (una vez con RLS): repetir 1–6.
8. Handler de outbox con `payload.tenantId='B'` mientras el contexto de sesión es A ⇒ el efecto se materializa **solo** en B (deriva del payload) y no cruza a A.
9. Verificar que `deltaops_app` **no** puede `ALTER`/`DROP`/`CREATE` (privilegios de estructura denegados) ni `TRUNCATE`.

Integración: extender los `*.pg.test.ts` existentes para correr también bajo `deltaops_app` (segunda `DATABASE_URL`), no solo bajo `postgres`. Durante este Discovery **no se modifican datos ni se ejecutan estos casos**.

## 16. Observabilidad

- **RLS violation / permission denied:** capturar `SQLSTATE 42501` (insufficient_privilege) y errores de policy; log con `tenantId`, `identityId`, `opId`, comando y tabla (sin PII sensible ni credenciales).

## 17. Impacto en producción

- **Cambio de runtime (Fase G):** es un cambio de **secreto** + reinicio del API. Downtime = ventana de reinicio (segundos); las conexiones del pool se recrean con el nuevo rol.
- **Migraciones (Fases A–E):** `ENABLE/ALTER … RLS`, `CREATE POLICY`, `GRANT`, `FORCE` — DDL rápido; `FORCE` toma lock breve por tabla (167 tablas). Planificar en ventana de baja carga.
- **Neon/Replit:** validar capacidad del proveedor para crear roles y ajustar ownership (STOP-2). Verificar que PostgreSQL no esté expuesto públicamente.
- **Backups/rollback:** tomar backup/branch antes de las Fases D/E/G (Neon ofrece branching/PITR — verificar). El rollback de RLS es granular (§14).
- **Pool:** sin cambio de tamaño; misma disciplina transaction-local.
- **Estrategia:** `dev → staging → validación (tests PG + E2E + A/B) → producción`. No pasar a producción sin PASS completo en staging con `deltaops_app`.

## 18. Criterios de aceptación (para la futura implementación — DGP-023.4)

La implementación posterior solo será PASS si:

- ✓ El runtime NO conecta como superusuario (`current_user` ≠ superusuario).
- ✓ El rol de runtime NO tiene BYPASSRLS (`rolbypassrls=false`) ni es owner de las tablas.
- ✓ Todas las tablas tenant-scoped tienen RLS (incluidas `idn_memberships` y `users`, o exención documentada y justificada).
- ✓ Las policies tienen USING y WITH CHECK correctos (predicado `tenant_id = current_setting('app.tenant_id', true)`).
- ✓ FORCE ROW LEVEL SECURITY donde corresponda (§12), tras validación.
- ✓ Tenant context fail-closed (sin GUC ⇒ 0 filas / rechazo).
- ✓ Pooled connections aisladas (transaction-local, sin fuga entre requests).
- ✓ Offline/sync tenant-safe (tenant derivado server-side, nunca del payload para autorización).
- ✓ Workers/outbox tenant-safe (tenant del payload; fail-closed si falta).
- ✓ Migraciones/seed separadas del runtime (owner/migration role).
- ✓ SUPER_ADMIN conserva capacidades legítimas (vía GRANT acotado o `SECURITY DEFINER` documentado, no vía bypass global).
- ✓ Ningún tenant cruza datos; SELECT/INSERT/UPDATE/DELETE cross-tenant bloqueados (batería §15).
- ✓ Tests PG reales PASS bajo `deltaops_app`; API E2E PASS; DeltaOps completo PASS.
- ✓ Login e identidad funcionan bajo el nuevo rol (no fail-closed en autenticación).
- ✓ Rollback probado y granular; sin "superuser permanente" como fallback.
